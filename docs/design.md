# jackalopefs design

A client/server network mount for Linux. One server exports one directory over QUIC; a client mounts it through FUSE. Both run as ordinary users. This document is the durable description of the protocol, the architecture, and the limits; the research notes that motivated it are in `research-fusex.md`.

## Goals

- Correct POSIX semantics with a single attached client; best-effort coherence with several.
- No dependence on ssh, NFS, or any other authentication system: anonymous by default, an optional shared token, TLS with a pinned server fingerprint.
- Never deadlock: every wait ends with a deadline, a lost connection, or a signal, on both sides, except the kernel's own writeback, which only the client aborting its mount ends. A vanished server produces errors, not hung processes.
- Parallelism where operations are independent (one QUIC stream per request), ordering only where it matters (the handshake and the event stream).
- Keep the client's kernel cache honest with server-pushed invalidation, with the cache TTL as the correctness backstop.

## Wire format (`jackalopefs-proto`)

The protocol is defined by two things together: the Cap'n Proto schema in `crates/proto/schema/jackalopefs.capnp`, which is the language-neutral description of every message, and this section, which states what the schema cannot. Cap'n Proto is used for serialization only. Its RPC layer would multiplex calls over one byte stream, which would undo the one-QUIC-stream-per-request design and its per-request cancellation, so it is not used.

**Streams.** Every frame is a little-endian `u32` byte length followed by exactly that many bytes holding one standard Cap'n Proto message (segment table followed by segment data). The body is at most 2 097 152 bytes, not counting the four-byte prefix; a decoder that reads a larger prefix closes the stream without reading the body. A single read or write payload is at most 1 MiB.

| Stream | Direction | Contents |
|---|---|---|
| first bidi, opened by the client | client → server | one `Hello` frame, then the client finishes its side; the server answers with one `HelloReply` frame and finishes. `Ack` carries the session id and resume token; `revisionMismatch` (the server's revision, checked before any token) or `reject` (bad token) is followed by the server closing the connection once the reply has been read. Request streams must not be opened before the `Ack`. |
| one bidi per request, opened by the client | client → server | one `Request` frame; one `Response` frame, server finishes. The client finishes its side after the request, except for a change (every request but the reads, `fsync` and the kernel's releases), whose side it finishes once it has read the reply: a client that gives up on a change resets that side and reads on, and the server answers by resetting its own, `unrun` or `fenced`, or with the reply if the change was done (Calls and deadlines); a reset that reached the server before the whole request did gets the stream finished with no reply, the request never read. A stream that ends before a complete frame arrived is a cancelled request, never a shorter valid message; the length prefix is what makes that detectable. Each side reads its peer's end of the stream, so that dropping it sends no STOP_SENDING: the server once the reply is out, waiting a few seconds at most, and the client when it arrives with the reply, without waiting. |
| one uni, opened by the server after the `Ack` | server → client | `Event` frames in order for the life of the connection: change batches for every session, and notices for this one |

Stream reset codes, which both ends read: 1 `stalled` (the server gave up on a reply the client did not read), 2 `cancelled` (the client gave up on the request), 3 `superseded` (the request came on a connection its session has since resumed on another, and was dropped unrun), 4 `unrun` (a change the client gave up on before it began, which will not run), 5 `fenced` (a change the client gave up on while it ran; the session's later changes wait for it). Connection close codes are each side's own.

Resumption: a client that reconnects sends its previous session id and resume token in `Hello.resume`; the `Ack` says whether the session was resumed (`resumed = true`, every handle still open) or is new. It also carries the export root's inode number and identity (`rootIno`, `rootIdentity`), and the effective uid and gid the server runs as (`uid`, `gid`), from which the client maps owners ("Ownership").

**Single segment.** Every frame body carries exactly one segment, so its segment table is the eight bytes `[0, length_in_words]` and the message contains no far pointers. Encoders must produce this (ours pre-sizes the first segment from the message and, if that estimate was short, canonicalizes into one segment; canonical form drops trailing zero words from struct sections, so the same logical message has more than one valid encoding and decoders must accept both). Decoders reject any other segment count. This is the rule that keeps a decoder in another language, or in a kernel, small.

**Reader limits.** A conforming decoder applies a traversal limit of four times the largest frame (1 Mi words), a nesting limit of 16 (the deepest real message is six pointer levels: `Response` → `List(DirEntry)` → `DirEntry` → `Attr` → `List(Data)` → `Data`; groups are inline), treats bytes left over after the message inside a frame as an error, and rejects a struct list that declares more elements than the message has words (a zero-sized element type would otherwise let a 40-byte frame declare a million entries). With those checks the memory a frame can produce is bounded by a small multiple of its size.

**Decoders reject.** These are checked while parsing, and a message that fails them is a decode error, not a filesystem error:

- A name (`Data`) is 1 to 255 bytes, contains no `/` and no NUL, and is not `.` or `..`.
- A path (`List(Data)`) is at most 4096 bytes when joined with `/`. The empty path is the export root, and so is an omitted path pointer: a null list pointer reads as an empty list.
- A resume token is exactly 16 bytes.
- `reason` in a rejection is UTF-8. Every other byte field, the auth token included, is arbitrary bytes compared as bytes.
- An unknown union discriminant or enum value (a peer speaking a newer schema) is a decode error, never a guess.

**Senders guarantee.** These cannot be checked by a decoder; a receiver treats a violation as an ordinary error on that request:

- `getattr` and `setattr` carry a path, a handle, or both, never neither (`EINVAL` otherwise); when both are present the handle wins and there is no fallback to the path.
- `fh` values are chosen by the client and never reused within a client's lifetime.
- A `fallocate` covers at most 64 MiB (`EINVAL` beyond that); a sender splits a longer range into consecutive requests, which every mode the protocol carries allows: any combination of `FALLOC_FL_KEEP_SIZE`, `FALLOC_FL_PUNCH_HOLE` and `FALLOC_FL_ZERO_RANGE`, the modes the FUSE kernel forwards. Another bit is `EOPNOTSUPP`.
- A `copyFileRange` may be answered with fewer bytes than `len`, as `copy_file_range(2)` may: `copied` says how many, and the sender asks again for the rest. How much a server copies per request is its own choice (ours: 64 MiB) and not part of the protocol.
- `err` is a Linux errno (the client clamps unknown values to `EIO`); `flags`, `mode` and `mask` are Linux values; `nextOffset` is a `getdents64` cookie.
- `end` in a `readdir` reply means no entry follows the last one returned, so a client may answer a further read at that entry's `nextOffset` itself instead of asking; it says nothing when the reply has no entries. It stays true across entries the server skipped after that one (a file that vanished mid-listing, a mount point): a read at the cookie re-reads and re-skips them and finds nothing.

**Optionals.** Every optional value is an explicit `none`/`some` union. For primitives that is the only representation Cap'n Proto has (a sentinel like mode 0 or uid 0 would be a real value); for pointer-typed optionals (`Option<Path>`, `Option<Attr>`) a null pointer would also work and is distinguishable from an empty list, but one rule is easier to implement than two and absence shows up in the text form.

**Attributes carry what the client is about to be asked.** `Attr.xattrNames` is the node's extended attribute names as `listxattr` returns them, as an explicit `unknown`/`some` union: `some` with an empty list states the node has none, which a client may answer `getxattr` (`ENODATA`) and `listxattr` from without a round trip; `unknown` means the server did not look or could not say, and the client must ask. The server answers `unknown` for a node with more than 1 KiB of names (so a listing page stays inside a frame) and on a filesystem without xattr support (whose `EOPNOTSUPP` a `getxattr` must return rather than the `ENODATA` an empty list would imply). Filling it costs the server an `openat` with `O_NOFOLLOW`, a `listxattr` and a `close` per node on top of the stat, and a symlink describes itself, never its target. A client answers only absence from the list; a name that is present is fetched every time and no value is cached. (A filesystem that lists names but refuses a namespace would answer a `getxattr` with `EOPNOTSUPP`; the client answers `ENODATA` for that name instead, which every caller treats the same.) This is the one place the protocol sends something before it is asked for; a general speculative fetch, if one is ever built, would subsume it.

**Layout choices.** Request variants are groups inside one union, so a request is a flat struct of six data words and four pointer words whatever its variant; the members overlap. Adding a field to any group can grow every request by eight bytes (`copyFileRange`'s five 64-bit fields, where no other variant has more than two, account for three of the six words; it is a group like the rest because one rule for every variant was preferred to saving 24 bytes with the only pointer-borne request), the accepted price for one fewer pointer hop and traversal charge per request. Timestamps inside `Attr` are groups, not `TimeSpec` pointers. Replies that carry an `Attr` (`entry`, `opened`), the `read` reply and the `readdir` reply are groups so per-reply fields can be added later without a break. `err` is the first `Response` member so an all-zero message reads as an error and fails closed. Measured: the smallest request (`release`) is 96 bytes on the wire, `ok` is 40 (`seeked`, the one 64-bit reply member, gives every reply a second data word), a 1 MiB write is 1 048 672, and a listed entry with a one-byte name costs 176 with ext4's 8-byte file handle (32 of them the entry, the rest its attributes); on a QUIC stream none of this is worth optimising.

**Evolution.** Union discriminant values follow ordinal order, not declaration order: reordering declarations keeps the wire format, renumbering ordinals changes it. `Hello`, `HelloReply` and every struct they reach (`Resume`, `Identity`) are frozen for ever, since peers of different revisions must still decode them to refuse each other and say why, and a server decodes the whole `Hello` before it compares revisions. Every other struct is decoded only between peers of one revision, so a new revision may renumber it, and removing a field requires that, as ordinals must stay contiguous; a field added without removing any is appended with a fresh, higher ordinal. A group's position in a union is its lowest member ordinal. The compiler accepts out-of-order ordinals without complaint, so a renumber will not be caught by it; the golden-bytes test in `crates/proto/src/codec.rs` exists to catch it. A decoder that meets an unknown discriminant or enum value reports a decode error rather than guessing.

**Revision.** `Hello.revision` is `PROTO_REVISION`: the 64-bit FNV-1a hash (offset basis `0xcbf29ce484222325`, prime `0x100000001b3`, one byte at a time in file order) of the schema file's exact bytes, comments included, computed when the proto crate is compiled. Any edit to the file is a new revision, on purpose, because the comments carry the rules the schema cannot express; the price is that fixing a typo there costs every peer a rebuild. The server compares it before authentication and answers `revisionMismatch` with its own; the server logs both values, the client logs them on a reconnect and prints them on exit when it is the first connection, and the connection is refused; there is no negotiation and no fallback yet. It detects accidents, not attacks: nothing authenticates the hello, and another implementation only has to reproduce the hash. It does not cover a rule that lives only in code (the reader limits, the list amplification check, the directory-entry cost, the ALPN); changing one of those is a protocol change and must come with a schema edit so the revision moves, which the comments at those definitions say. The field reuses ordinal 0 with a wider type than the old `protoVersion`, so a peer from before revisions cannot read a valid version and accept: an old server fails to decode the new hello, and a new server refuses an old hello (whose first word reads as revision `1`, or `0x0001000100000001` with a token and a resume) with a variant the old client cannot decode. Both refuse; only pairs built after this change get the diagnosis.

**Generated code.** The Rust readers and builders are generated at build time by `capnpc`, which shells out to the `capnp` compiler; that is a build requirement documented in the README. The generated code is not checked in: it is fifteen thousand lines that would sit in every commit, and a test asserting it matched the schema would need the compiler anyway. Zero-copy delivery of read payloads (handing the kernel a slice of the frame buffer) is a follow-up; today each `Data` field is copied once out of the frame, the same count as before.

## Server (`jackalopefs-server`)

**Export root and path resolution.** The export directory is opened once as an `O_PATH` fd. Every client path is resolved with `openat2(root, path, RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_XDEV)`, either to the node itself (an `O_PATH` fd pinning the inode) or to its parent directory plus a single validated component for the `*at` family. No multi-component client path reaches any other syscall, so a symlink or mount point inside the export cannot lead outside it. Operations with no `*at`/`AT_EMPTY_PATH` form (chmod, xattrs, access) re-enter the pinned fd through `/proc/self/fd/N`. A listing is described from the directory's own fd, one `statx` (whose mount-root attribute refuses a mount point as `RESOLVE_NO_XDEV` would) and one `llistxattr` (through `/proc/self/fd/N/name`) per entry, so listing opens nothing; an entry the server lacks the descriptors or memory to describe fails the page rather than being left out of it. Requires Linux 5.8 or later; the server probes `openat2` and `statx` at startup.

**File identity.** An inode number does not say which file is meant. Filesystems hand a freed number to the next file (ext4 to the very next one created), and `RESOLVE_NO_XDEV` stops at mounts, which a btrfs or bcachefs subvolume is not: a snapshot shares every inode number with its origin, inside one export. So every `Attr` carries, with the filesystem's own inode number, the file's identity: its `name_to_handle_at(2)` handle, type and bytes, as the kernel gives it (on ext4 the inode number and a generation re-drawn at every allocation; on btrfs and bcachefs the subvolume as well). It goes on the wire unparsed and unhashed, because the generation exists nowhere else a server can portably get it (no `stat` field; `FS_IOC_GETVERSION` needs a real open descriptor, which a listing must not take, and does not work on symlinks or sockets), and sits inside the handle at offsets only a per-filesystem table could decode. The handle is the same by any route to the file (by name, by descriptor, through a hardlink, after a rename), needs no privilege, and is asked for with `AT_HANDLE_FID` where the kernel knows that flag (6.5), which works even on a filesystem without export operations; the two forms are the same bytes wherever both exist. Whether the export's filesystem gives handles at all is settled at start-up, on the root: a server refuses to serve one that does not, because it could not tell its files apart, and thereafter a failure to get a handle fails the request rather than sending an attribute without one. A listing opens nothing, so it resolves each name several times over; the handle is taken before and after the `statx`, and an entry whose two handles differ is left out as one that vanished mid-listing, since a client keys its nodes by the pair and must never be given one file's identity with another's attributes (measured: once in 25 000 on a name unlinked and recreated in a loop). The identities cost a listing two more syscalls an entry and a lookup one: measured on loopback with debug builds, the server's time for a page of a 10 000-entry directory went from 5.5 ms to 7.6 ms and the listing from eight pages to nine, a cold `ls -l` of it from about 340 ms to about 420 ms, and 10 000 lookups did not move. Equal handles mean one file throughout, a recycled number coming with a new generation; a name renamed away and back between the calls can still pair that file's identity with another's `statx`, the race every lookup by path has. `Attr.foreign` says the file lies outside the export root's subvolume, by `statx`'s `stx_subvol` where the kernel reports it (6.10) and by `st_dev` otherwise: bcachefs gives all its subvolumes one device number, btrfs gives each its own. The root is described by its own inode number like anything else, and the `Ack` of every hello carries its inode number and identity.

**Threads.** The network runs on one tokio worker (`jackalopefs_perf::runtime`), the filesystem work on the blocking pool, and the server's accept loop on the main thread, which runs the runtime's `block_on`; the server's signals are handled in a task on the worker, and its periodic report, which reads `/proc` and sysfs, runs on the blocking pool. Each request is its own QUIC stream and task, and every stream of a connection locks quinn's state for that connection to move its data, so workers beyond one serving one client only contend for that lock and wake each other to steal work: measured on loopback with small requests, a second worker made each request cost more CPU, and going from 32 workers to one cut each request's CPU by about a third on the server and nearly half on the client while throughput rose (`scripts/perf/bench.sh`). One worker reads the UDP socket only between the tasks it runs, so both sides ask for a 4 MiB receive buffer (`net.core.rmem_max` caps it, and a process granted less says so at startup): with the kernel's default of about 200 KiB the sockets overflowed in bursts, doubling packet loss and shrinking the sender's congestion window tenfold. The blocking pool keeps a slow disk off the network thread. `TOKIO_WORKER_THREADS` overrides the one worker.

**Operations** run on tokio's blocking pool, one task per request stream, and no syscall reachable from a request may block indefinitely: every open is `O_NONBLOCK` (all I/O is positional, so the flag changes nothing for regular files) and only regular files and directories can be opened through a handle, since the FUSE kernel handles FIFOs, sockets and devices itself and never asks the server to open one. Files are read and written positionally (`pread`/`pwrite`), so concurrent requests on one handle need no lock (an `lseek` for data or a hole does move the descriptor's position, which nothing reads); a directory handle's read position is shared state and is serialised per handle. Directory listings use `getdents64` and return the real `d_off` cookies, so a client `readdir(offset)` is a genuine `seekdir`; the `.` and `..` entries carry what `getdents64` gave, and the client, which knows both directories as nodes, puts their numbers in. The server runs with `umask(0)` because the client kernel has already applied the caller's umask, and creates its own state files with explicit modes. `mknod` accepts regular files, FIFOs and sockets; device nodes need `CAP_MKNOD` and are refused.

**Sessions and resumption.** Each connection attaches to a session holding the open-handle table. When a connection drops, the session is detached and kept for a 60-second grace period; a client that reconnects with the session id and resume token gets the same handles back, including files that were unlinked while open. Past the grace, a session whose requests still run (a change stuck in the filesystem) is resumed all the same, so that change stays ordered before the client's next ones. The server closes the connection a resume takes over (close code 3, `superseded`), since the client has given up on it, and likewise a connection whose resume another one of the session's overtook. A resumed connection's requests that change something (everything but the reads, `fsync` and the kernel's releases) wait until every change still running from the session's earlier connections has finished, on any file: a coarse barrier, which keeps a change whose reply was lost from landing after its resend or after the client's next change. A change from an earlier connection that has not begun by then is dropped unrun and its connection closed, since the client has already resent it or failed it. A change the client gives up on while it runs (an interrupt, `--op-timeout`) holds the session's later changes the same way until it finishes, and one it gives up on before it has begun is dropped unrun (Calls and deadlines). A held change is dropped unrun if its caller gives up on it or its connection goes, and held changes occupy request streams, so past the 1024 a connection may have open even reads queue behind them. The client chooses handle ids and never reuses one, so when an open's outcome is unknown (timeout, lost connection, malformed reply) the client asks the server to release that id: releasing one that was opened closes the fd. That release is ordered (`Release.ordered`): it goes out once the server has answered the open's cancel, and if the open still runs it is held behind it like any change, so the open, should it still be on its way, keeps no descriptor nobody would release. So are the client's other releases of its own (a handle a reopen lost, a release owed); one held and then given up on, or dropped with a superseded connection, is owed and sent again. The kernel's release follows its open's reply, so it is not ordered: a late one changes nothing a later request finds. A retried open whose id the session still holds is a resend whose original ran and kept its handle: it answers from that handle and opens nothing. Opens are ordered even when they change no file: an open from a superseded connection that ran late would replace a live handle with whatever file is at its path by then. A client that reconnects to a different one of its server's addresses presents a session the server there may know nothing about; an unresumable session id is answered with a fresh session rather than a refusal, and the client reopens its handles. Every open handle is a file descriptor; the server raises its soft open-file limit to the hard limit at startup, and every session's handles draw on one pool, what is left after 2048 reserved for its own work (half the limit, when the limit is smaller): 522240 at the common limit of 524288. An open is refused with `EMFILE` only when the pool is full. A session's share is the pool divided among the 64 connections the server accepts plus the 64 sessions that may wait detached at once (the oldest is dropped early), 4080 at that limit and never more than 16384; a session past its share is reported, not refused: a warning names the client's address and session, what it holds by kind and how full the pool is, at the share and again at each doubling of it, and afresh only once the session has fallen under half its share, so one that hovers at its share is reported once. Each report also sets a notice on the session (`Event.handles`, with what it holds and its share, in a frame of its own on the session's event stream, numbered there with the batches), which asks the client to log what holds its handles; it is cleared once written, or when the session falls under half its share, and one still set when a connection attaches (its last connection went before writing it) is sent first on the new one. The client's answer names processes, which it never sends: one warning line with the server's count, the share and its own count by kind (the client's trails by the opens whose replies are on their way, the one that crossed the threshold among them; a larger gap is handles the server holds that the client has forgotten, or is still releasing), then the ten largest rows of `jackalopefs-ctl handles` and a line for the rest, built on a blocking thread; the client event `handles_reported` counts the notices. The event `handle_share_exceeded` counts those reports, `handle_pool_full` every open the full pool refused and `handle_fds_exhausted` every one the process's own descriptor limit refused; a slot is taken before anything is opened, so a refused open (a create, a truncation) has changed nothing. Refused opens are logged the first time and then at most every 10 s with how many were refused since and over how long, and what is left unlogged when the connection ends is logged then. The periodic report lists each session's handles by kind and the pool's use.

**Change notification.** The server watches the directories clients use, not the whole export. A client can only cache what a request fetched, and every request names its paths, so before a request runs the server places an inotify watch on each directory it names: the parent of every path, and the directory a listing opens. A directory's watch reports changes to its entries and to its children's contents and attributes, subdirectories included, so whatever a reply lets a client cache is reported from then on. The directories a request named stay watched until its reply is sent, and a handle keeps the directory it was opened in (a directory handle, the directory itself) watched until it is released, since the kernel trusts what it caches for a file held open; requests on a handle name no directory of their own.

The watched directories form a tree under the export root, which is watched from startup: a directory is watched only once its parent is, and is resolved inside its parent's descriptor after that, so the move or removal of any watched directory is reported on a watched parent, and the server keeps its record of what is watched where in step. A directory moved within the export keeps its watches under its new name when both halves of the move arrive together; one moved out of sight, removed, or renamed over is dropped and announced. Before acting on such an event the server checks that the directory it has at that path is still the one there, since a request may already have watched the directory under its new name, and a request that goes below a watched directory checks it the same way, in case it was replaced by an event not applied yet. A directory the server cannot watch (no read permission) is served unwatched, retried a minute later, and nothing below it is watched, since a rename there would go unseen. A watch the server drops it drops first and then announces with an `Unwatched` notice, and clients drop what they cached under that directory (Invalidation); a later request watches it again.

The server watches at most `--watch-limit` directories besides the root, by default half of `fs.inotify.max_user_watches` (which every process of its user shares) and at most 65536, since each watch pins its directory's inode in kernel memory. Past that it drops a batch, at most 512 at a time (each removal queues an event in the same inotify queue the changes come through), or as many as it takes to get back within the limit: the directories used longest ago, counted in rounds between batches, with nothing watched below them and nothing holding them. When the system runs out of watches before the limit does (other processes of the same user hold the rest), the server warns and watches no more than it has for ten minutes. The perf report gives the number watched and the limit, and the events `watch_evicted`, `watch_unwatchable`, `watch_limited` and `inotify_overflow` count the directories dropped, the ones that could not be watched, the times the system ran out, and the queue overflows, each with the path it concerned as its detail.

The watches feed a 100 ms debouncer that deduplicates items and broadcasts one batch per window to every session. Each mutating request records `(path, session)` first; the inotify event it produces consumes that record, so the originating session is not told about its own change while a later change to the same path by anyone else is reported normally. A session that falls behind the broadcast produces a single `Overflow`, and so does an inotify queue overflow, after which the server checks every watched directory against the filesystem, since the lost events may have moved or replaced any of them, and drops, announced, those no longer where it has them. If the export root cannot be watched the server logs an error and runs without notification, and likewise if the root's own watch ends.

**Transport.** TLS 1.3 only, ALPN `jackalopefs/1`, a self-signed certificate generated once and persisted in the state directory so its fingerprint is stable. Idle timeout 10 s; per-stream receive window 2 MiB; connection receive and send windows 64 MiB (quinn's default receive window is unbounded, which an anonymous peer could turn into memory exhaustion); at most 1024 request streams per connection and 64 connections. Directory listings are budgeted against the actual Cap'n Proto entry size so a full `MAX_IO` page of entries stays well inside a frame.

## Client (`jackalopefs-client`)

**Connection manager.** One background task owns the QUIC connection. The server name is resolved once, at mount, into a list of candidate addresses; every attempt tries them in order on its own connect deadline until one completes the hello, and the address that answered is tried first from then on, so a dead candidate ahead of it costs its deadline once rather than on every reconnect. A refusal (bad token, foreign revision) ends the sweep instead of moving on, since every address behind the name would answer the same. Each address family among the candidates gets its own socket rather than one dual-stack socket, because whether an IPv6 socket also reaches IPv4 peers is the host's decision (`bindv6only`, a sandboxed `setsockopt`); a family whose socket cannot be bound costs only its own candidates, which are dropped with a reason at mount. Every failed candidate is logged, and the failure the caller is told about is the most informative one rather than the last, so an address that answered with a bad fingerprint is not buried by one that never answered at all. It connects, completes the hello, then either resumes (nothing to do) or reopens every live handle by path, concurrently, marking stale those that fail or whose path now leads to another file. Only then does it publish the connection, and releases the stale ones on the server after, and from then on every release owed (one that timed out, or found no connection) as it is owed; each reopen carries the offline deadline (reopening is part of getting the connection back, and until it is done every call is waiting, or failing at once if the outage is already past its deadline), so the phase takes at most one of them. When the connection closes it retries with exponential backoff (100 ms to 5 s) forever, until unmount. Keep-alive pings every 3 s detect a vanished server within the 10 s idle timeout. The same file means inode number and identity both: an inode number alone may be another file's by then. And a mount is of one directory: the root's inode number and identity come with every hello, and a server that returns describing another root (the export replaced or restored, a filesystem whose handles did not outlast a remount) is another export, so every open handle goes stale at once, which is logged as an error, and what the kernel caches is swept as after any reconnect.

**Calls and deadlines.** A call has two waits with different clocks. Waiting for a connection is bounded by the offline deadline (`--offline-timeout`, default 15 s), set when the call starts and renewed only for the one resend a lost reply gets, and also by the outage's own deadline: the manager publishes when the connection was lost along with `Connecting`, and a call waits no later than that moment plus the offline timeout. In effect a call waits until the outage is that old, and only before the manager has seen the loss (a stream failing on a connection still published) does its own deadline bind. Without the outage bound every call made through a long outage would wait out a deadline of its own, and a program making one call after another (`ls -l`, a shell prompt, an editor's file watcher) would take minutes per screenful, while the kernel's inode locks held by those waits queue other processes behind them in uninterruptible sleep. The outage is counted from when the loss is detected, which the idle timeout puts up to 10 s after the network goes, and it lasts until the next attempt succeeds, so fail-fast can outlast the network's return by a backoff step and a connect attempt; a loss after a published connection, however brief, starts a fresh outage. A release that fails for want of a connection, or times out, is owed: the handle table keeps it, and the manager's release task sends it on the connection that is up, at once if one is and after a reconnect that resumes the session if not (once the connection is published, so a server slow to answer holds up no call, for as long as that connection lasts, owing again whatever goes unanswered; the next connection waits for these sends to end, so nothing owed again is missed), and drops it with a session the server has forgotten, since a new session holds none of the old one's handles; releasing an id the server does not hold is harmless. The releases of handles found stale by a reopen go the same way. The manager logs one warning per outage once it has lasted the offline timeout, and the reconnect line says how long it lasted, both counted from when the loss was detected. The exchange itself, once the request is on a live connection, is bounded only by the optional `--op-timeout` (unset by default), because a server slow to answer is not an error and the connection's idle timeout fails the exchange if the server dies. When either deadline passes, or the kernel interrupts the request the call is made for, the call fails at once (`ETIMEDOUT`, `EINTR`), and whether the operation was applied is unknown. A read's receive side is stopped, and the server, which may still run it, sends nothing more. A change's send side is reset and its reply stream read on in the background, and the server answers what became of it: `unrun` if it had not begun (it never will), `fenced` if it is running (the session's later changes wait for it), or the reply if it was done. Until that answer arrives, the client sends no other change on that connection; reads go on. So an abandoned change never lands after the caller's next change, and an interrupt is immediate even when the server is gone: the next change waits for the server as it would anyway, and that wait is itself given up on at once, with nothing sent. A lost connection answers for every pending cancel, and its changes are ordered by the resumed session. A lost reply is unknown too, but once the session resumes the server runs none of the lost connection's changes after one of the new connection's. A request that was never sent simply waits for the next connection. A request whose reply was lost with the connection is resent once on the next connection only when that cannot change the outcome: lookups, stat, setattr (every field is absolute, a time set to now aside, which a resend moves on), readlink, reads, opendir, readdir, release, releasedir, fsync, statfs, xattr reads, a setxattr without flags, access, `copy_file_range`, `fallocate`, `lseek`, opens without `O_TRUNC`, creates without `O_EXCL`/`O_TRUNC`, writes not through an `O_APPEND` handle (the server appends those at its own end of file; through the mount none is, since the kernel places appends itself). Everything else fails with `EIO`.

Errnos: `ETIMEDOUT` when a deadline passes, `EIO` when the connection was lost mid-request, `EINTR` when the kernel interrupted the request, `ESTALE` when a node or handle no longer refers to the file it did, `ECONNABORTED` for a request pending when the mount was aborted, `ENOTCONN` after unmount.

**Node table.** A node is one file on the server, known by its inode number and identity together; hardlinks share a node. Each node has one number, which is the FUSE node id and what userspace sees as `st_ino` (fuser has one field for both). It is the file's real inode number for a file in the root's subvolume whose number no other node holds, which is nearly every file: tools that record inode numbers (git's index, borg, restic, incremental tar) see stable, real ones, tree walkers that sort by `d_ino` keep their on-disk order, and `ls -i` matches the server. Otherwise it is a substitute, a fixed 64-bit hash of the handle (moved off 0 and 1, which the kernel reserves, and onward while taken): always for a file outside the root's subvolume, so that a snapshot's tree shows the same numbers on every walk (short of two hashes colliding, where the later one seen moves on) and a snapshot's file differs from its origin in `(st_dev, st_ino)`; and for a file whose inode number is still held by another file's node, a recycled number whose previous owner the kernel has not forgotten, which is the one case that depends on what was seen first (the file shows its substitute until both nodes are forgotten, then its real number). A node's number is never given to another file while the kernel remembers it, so every node has generation 0 for ever. The root is node 1; the client rewrites the root's inode number to 1 as replies come in. For each node the table keeps the `(parent, name)` aliases it has been reached through and the kernel's lookup count, and addresses it by the newest alias whose directory it can itself still address (the kernel forgets a directory nothing holds, while a file with a name in it may be held through a name elsewhere). When the last known alias disappears (unlink, rmdir, rename-over, or a lookup finding another file under the name), the node is marked unlinked, which says only that this client has no name for it: finding the same file again under another name gives the same node back, so a descriptor opened through the first name keeps working. A reply that should describe a known node and describes another file (`getattr`, `setattr`, the source of a `link`, an `open` or `opendir`) means the name led elsewhere, renamed or replaced by someone else; the kernel checks nothing of the kind and would take the other file's attributes for the inode it asked about. The client drops that alias, invalidates that name in the kernel, and tries the node's next alias; `ESTALE` is the answer only when none is left, and a path-based caller then retries with a fresh lookup by itself. A `setattr` down a path that led elsewhere has changed that other file by the time the reply says so, and `rename`, `unlink`, `rmdir`, `readlink` and the xattr calls return no attributes to check at all: inherent to addressing by path. An unlinked node with no handle open cannot be addressed by this client (which is not to say the file is gone: it may live on under a hardlink the client never looked up, or a name it lost to a rename on the server), and one request still arrives for it: with the kernel caching writes it keeps a regular file's times itself and flushes them, by a `setattr` that names no handle, from inside the `unlink` or `rename` that removed the last name. The client answers that flush itself and sends nothing (the server stamped any surviving link with its own unlink, and the kernel ignores the reply); an error there is recorded against the whole mount and fails the next `syncfs(2)`. It recognises the flush by its shape, a modification time given as a value and nothing else, so a `utimensat` of just that through an `O_PATH` descriptor on such a file is answered the same way: not applied, reported as done, and the placeholder attributes of the reply (no permissions, no links) are what the kernel then holds for that inode until it asks again, which fails with `ESTALE` as before. Every other request for such a node still fails with `ESTALE`. The table is guarded by a `parking_lot::Mutex` that is never held across an await or a notifier call.

**FUSE backend.** Each kernel request is copied out of the session thread and answered from a tokio task; the session thread never waits on the network. The tasks run on the same single worker as the connection (see the server's "Threads" for why), and each answers with a synchronous `writev` to `/dev/fuse`, which copies the reply (up to 1 MiB) but never waits on a kernel lock; the calls that can, invalidations, have their own thread. `init` asks for 1 MiB `max_write`/`max_readahead`, 64 background requests, and `ATOMIC_O_TRUNC | ASYNC_READ | PARALLEL_DIROPS | AUTO_INVAL_DATA | DO_READDIRPLUS | READDIRPLUS_AUTO | WRITEBACK_CACHE`. The kernel caches writes: a `write(2)` returns once the page cache has the data, the kernel sends requests of up to `max_write` with up to `max_background` in flight, and `close(2)` and `fsync(2)` write everything back and report any failure, flattened to `EIO` at close, before the request reaches this daemon, which buffers nothing of its own. Before a `write(2)` on attributes older than the TTL the kernel refreshes them with a `getattr`, whose reply carries the xattr names, which is why its per-write `security.capability` probe is answered from the metadata cache. The kernel reads through write handles to fill the rest of a partially written page and positions appends itself, so the server is asked to open every file for writing as `O_RDWR` and never with `O_APPEND` (a server-side append would put every re-flushed page at the end); a file writable but not readable cannot be opened for writing through the mount unless the server can read it anyway (it runs as root). `keep_cache` is not set on purpose: the page-cache drop on every open is what still bounds a stale cache for a file nobody holds open. Entry and attribute TTLs default to 1 s. Directory reads fetch 256 KiB of entries at the start of a listing and 1 MiB (the most a reply carries) after that, every entry but the dots with its attributes (the first fetch is smaller because many readers stop after a few entries, an emptiness check or a file manager's "has children" probe, and the server describes every entry it sends; a 100 000-entry listing takes 22 round trips), and serve the kernel's smaller pages (its caller's `getdents64` buffer, 32 KiB for glibc) from a per-handle buffer keyed by cookie. The kernel asks for the first page as readdirplus and later ones as plain readdir unless a stat in between told it otherwise, and either kind is served from the same fetch, except that a readdirplus page, whose attributes the kernel caches, is not served from a buffer fetched longer ago than the attribute TTL: a readdirplus page links each entry's node, and a plain page lists each entry under the number the node table gives the file without registering it (`id_for`, what a lookup would register), so `d_ino` is what `stat` reports, a substitute included, short of the order-dependent cases the node table describes (another file claiming a colliding number in between, or the holder of a number being forgotten), and of a name replaced on the server within the entry TTL, which the listing shows as the new file while `stat` still reports the kernel's cached one. Every listing leaves out the same entries, those the server cannot describe: a mount point, a name that vanished mid-listing. Each handle also keeps the cookie at which its last fetch said the directory ended, and answers a read there without a round trip, which is how a complete listing costs one fetch rather than one plus an empty tail. A handle left open after a full listing sits at exactly that cookie and reads there again, so the cookie is cleared whenever a name is added under the directory, by this client or in a server event, and the read goes to the server, which answers as the export's filesystem does for a local handle at that position (a hashed or newest-first order usually puts the new name before it); the cookie is otherwise replaced by the next fetch, and offset 0 always goes to the server so `rewinddir` and a fresh `opendir` see everything. What a parked handle still misses is an addition the server never reported, which the entry TTL does not cover either. The cookie survives a reconnect because `getdents64` cookies are stable across opens of the same directory, the same fact the reopening of directory handles by path rests on. `.` and `..` map to the directory's own and parent nodeids and never take a lookup count; a readdirplus entry takes one only when fuser's buffer accepted it. `fsync` and `fsyncdir` go to the server. Locks (`getlk`/`setlk`/`flock`) are not implemented, so the kernel handles them locally, which is correct for a single client. fuser itself is vendored under `vendor/fuser` (a workspace member, so its unit tests run with the suite); `vendor/README.md` lists the local patches it carries.

**Metadata cache.** The client keeps, per inode it has told the kernel about, the xattr names the last `Attr` carried (`xattrNames`), for the attribute TTL, so `--attr-timeout 0` disables it. From that it answers exactly two things without a round trip: a `getxattr` for a name not in the list, with `ENODATA`, and `listxattr`, with the names each followed by a NUL. A name that is present is fetched every time, so no value is ever stale. The entry is dropped on `forget`, on the client's own `setxattr` and `removexattr`, on a data event for the inode (a `setfattr` on the export arrives as one), and wholesale on a sweep. The kernel caches no xattrs for FUSE, so without this a file manager probing every entry for ACLs paid a round trip per probe; KIO makes two per entry. The `access(2)` storm the same file managers make is answered by `--default-permissions`, which has the kernel check mode bits against the calling user and never send `FUSE_ACCESS`.

**Invalidation.** Server events resolve through the node table to `inval_entry(parent, name)` and `inval_inode(ino)` calls. These are blocking writes to `/dev/fuse` that can wait on kernel directory locks, so they run on a dedicated thread fed by a bounded queue. Two things follow from the writeback cache. The kernel keeps its own size and mtime for every regular file it holds and ignores what the server reports, since its cache may be ahead of the server, so an inode invalidation cannot correct them; what does is taking the file away from the kernel by name, because an inode nothing references is evicted at once and the next access looks it up afresh. A data event for a regular file therefore also invalidates every entry the node table knows it by, and the attribute refresh is the backstop: when any reply carrying attributes (`lookup`, `getattr`, `open`, a `readdirplus` entry) disagrees with the size or mtime the server last reported for a file this client does not hold open, the same entry invalidations are queued, so an external change is seen within the attribute TTL plus one access (the access that detected it still sees the old size). A file this client holds open, in any mode, cannot be evicted and keeps the kernel's view until it is closed. A file this client wrote is dropped by name when its last handle closes, so the next access fetches the server's size and mtime: the kernel does not always push its mtime at close (a write in the same clock tick as the file's previous change leaves the inode clean), and the server's mtime is then the time the data arrived, milliseconds after the write. For a file held only for reading, the record of what the server reported stays behind, so the first refresh after the close drops it. Second, invalidating the pages of a file this client is writing would first write its dirty pages back, on the notifier thread, for as long as the network takes; for such a file only the attributes are invalidated, since the kernel's copy is the authority for it anyway. After every reconnect, and on `Overflow`, the client invalidates every open file and up to 4096 known directory entries, and every directory handle parked at the end of its listing asks the server again; the TTL covers anything beyond that. An `Unwatched` notice (the server stopped watching a directory) invalidates the directory's own entry, which drops every unused entry the kernel caches beneath it and their inodes with them, plus the attributes and pages of each file this client holds open in that directory, which nothing evicts, and the end a parked handle recorded for it.

## Failure model

This section is normative. It states what the client and server keep through connection loss, cancellation, resends and restarts, as invariants with IDs, the mechanisms that keep them, and the known gaps where the code does not. A change to recovery names the invariants it keeps and the mechanism it touches, or changes this section; a gap found is listed here, and staged in the disconnect grid where it can be. `docs/research-verification.md` surveys how to check it mechanically.

**State.** Per session, on the server, under its attachment lock: `epoch`; `running` (changes begun on the connection at `epoch` and not finished), `abandoned` (those of them the client gave up on), `running_older` (changes begun on earlier epochs and not finished); the handle table `fh → file`. Per change on the server: the epoch of its connection, and its phase: `Held` behind the fence or `Ready` for a thread, then `Running`, `Abandoned` (given up on while it ran) and `Finished`, or it ends unrun, `Cancelled`, `Superseded`, or `Dropped` with its stream while held. Per connection on the client: its `generation`, and `cancels`, the changes given up on whose answer has not come. A *change* is a request that takes part in the ordering: every request but the reads (lookup, getattr, readlink, read, readdir, the xattr reads, access, statfs, lseek), `fsync`, and the kernel's releases (`Request::changes`); a release the client sends on its own is a change. An open is a change even when it changes no file (S3). The session is *live* while it is in the server's table: attached, or detached within its 60-second grace.

**Events.** On the client a call *starts* and *ends*; a call for a kernel request ends when it answers the kernel. On the server a change *begins* (it is counted in `running`, `SessionState::begin`) and *finishes* (the count is dropped, `GuardExchange`). "b after a" means b's call started after a's call ended.

**Outcomes.** What the server did with a request is one of: never had it whole; dropped it unrun (`superseded`, `unrun`, or held and then given up on); ran it once; ran it twice (S2); ran part of it (G7, G8). What the caller learns:
- a reply: it ran; for a request of several steps (a `setattr` with several fields, a write past one `pwrite`, a create, mkdir, symlink, link or mknod that fails after making its entry, an `O_TRUNC` open that fails after truncating), an errno can follow the steps that succeeded (G7);
- `EINTR` or `ETIMEDOUT`: anything, from not sent to ran (the caller cannot tell a call that ended waiting for a connection, or for the answer to an earlier cancel, from one that ended waiting for its reply);
- `EIO` after a lost reply that may not be resent, or a reply that did not decode: anything.

**Safety invariants.**
- *S1, no overtaking.* For changes a and b of one live session, b after a and a's outcome unknown to the client (its call ended with no reply): a never begins, or a finishes before b begins.
- *S2, bounded repeats.* A request runs at most twice. It runs a second time only as a resend (M3): its reply was lost with its connection, it is in `retry_safe`, and it is sent once more, on a newer connection; for a change on a resumed session, after its original finished or was dropped. Two runs end as one run would only if nothing changed the same state between them; another session can (G2), and a `setattr` of a time to now moves it again. Releases owed are sent again too, and a new session reopens its handles under their ids; both are harmless repeats.
- *S3, handles.* Once nothing is in flight, the server's handles for a session are exactly the client's live ones. In particular an open's handle is never replaced by another file's, and no descriptor outlives the client's interest in it.
- *S4, durability.* When `fsync(2)` on a file succeeds, every write to it whose call succeeded before the `fsync` began is on the server's disk, unless the server's machine restarted since the write reached it (G6).

**Liveness.**
- *L1.* An interrupted or timed-out call returns at once, wherever it is waiting, the wait for an answer to an earlier cancel included.
- *L2.* A change waits for: the session's earlier connections' changes still running, and the changes this session gave up on that are still running (S1's price), however long those take in the server's filesystem, the session's grace included, since a session is resumed while any of them runs; then for its connection's pending cancels to be answered, about a round trip, or for as long as a server whose connection lives but which answers nothing keeps it. Held changes occupy request streams, so past the 1024 a connection may have open even reads queue behind them. The kernel's writeback is changes and is never interrupted, so it waits the same way. The client's own releases wait too, in the background: a descriptor stays open on the server until the open it may race has been answered for.

**Mechanisms.**
- *M1, epochs (S1, S2).* `Sessions::resume` increments `epoch` and moves `running` into `running_older` under the attachment lock; `begin` counts a change under the same lock and refuses one whose epoch is stale (`superseded`), whose connection is then closed, as is the connection a resume takes over. A change of the current epoch waits, before it begins, until `running_older + abandoned` is zero (`SessionState::drain`). A session dropped from the table (grace run out, or evicted as the oldest of 64 detached) is kept aside for as long as anything of it lives, since every request task and every running change holds it, and a hello naming it resumes it like any other; the table's lock covers the lookup and the attaching, so no drop comes between them. A client that only lost its connection therefore gets a new session only once nothing of the old one can begin or is running.
- *M2, cancels answered (S1).* For a change given up on, the client resets its side of the stream and keeps reading, and the server answers by resetting its own: `unrun` if the change had not begun (`Cancelled`, and `begin` refuses it), `fenced` if it is running (`Abandoned`, counted in `abandoned`, and M1's wait covers it), or with the reply if it was done. Its correctness rests on three orders, which a refactor must keep: the server updates its counts before it sends the answer; the client counts the change in `cancels` before the call returns; and a change's call checks `cancels` is zero, at its start, before it sends. A lost connection ends every pending answer, and M1 takes over. A read given up on is reset and stopped without an answer.
- *M3, resends (S2).* `retry_safe` names the requests that may be resent; a resend waits for a newer connection, where M1 orders it after its original if it is a change.
- *M4, handles (S3).* Handle ids are chosen by the client and never reused. An open of unknown outcome is released in the background (an orphan release); a release that fails for want of a connection, or times out, is owed: the connection's release task sends each one owed as it is owed, and one it could not deliver goes to the session's next connection if the session resumes. A release the client sends on its own (orphan, owed, or of a handle a reopen lost) is ordered: it waits for its connection's pending cancels, a reopen given up on counted among them, and then behind any open of its id still running, so no open lands under an id after its release; one held and given up on, or superseded, is owed. The kernel's release follows its open's reply and is not ordered. A resent open whose id the server already holds is one whose original ran and kept its handle (M1 has the original finish first): it answers from that handle and opens nothing, so it neither fails where the original succeeded nor replaces anything. Opens are changes (M1), so one from a superseded connection never replaces a live handle.
- *M5, durability (S4).* `write(2)` returns once the kernel has the data in its page cache; writeback sends it later, positional and resent once if its reply is lost. A writeback write that fails is not retried: the kernel keeps the pages clean, `fsync(2)` reports the error once per open file, and `close(2)` reports it if nothing reported it first (`ENOSPC` as itself, anything else as `EIO`); the data reaches the server only if written again. `close(2)` waits for the file's writeback but makes nothing durable. `fsync(2)` writes the file's pages back and then syncs the server's descriptor; on a directory it syncs the server's directory. A file opened `O_SYNC` or `O_DSYNC` is opened so on the server, and the kernel syncs after each write. `sync(2)` and `syncfs(2)` write the client's pages back and sync nothing on the server. A write on the server is in its page cache, which survives the server process but not its machine; creates, renames and other namespace changes are as durable as the server's filesystem makes them until an `fsync`. An `fsync` does not wait for a change given up on that is still running.

**Not ordered.** Reads, `fsync` and the kernel's releases take no part in S1: a read can see the state from before a change of unknown outcome, or before one it raced. What the client caches from such a read is corrected only by the TTL, since the server sends a session no events for its own changes; and for a file this client holds open, the kernel keeps its own size and mtime until the close, so a truncate given up on that ran later leaves the kernel's size stale while the file stays open. Changes from different sessions are ordered only by the server's filesystem. The fence is per session, not per file.

**Gaps.** Places the code does not keep the invariants, each a candidate fix:
- *G1 (S1).* A client that restarts or remounts starts a new session, and its old session's changes still queued or running are ordered against nothing: `begin` compares epochs only, so one queued on the old connection can begin arbitrarily late, after the new session has moved on.
- *G2 (S2).* A resend can undo another session's change: client A's write is applied, its reply lost; client B writes the same range and is answered; A's resend writes again. Likewise a punch or zero, a copy, a `setattr`, a `setxattr` without flags, a create without `O_EXCL` (re-creating a file B removed).
- *G6 (S4).* A server whose machine restarts loses writes it had acknowledged and not synced, and nothing tells the client: the next `fsync` runs on a new session and succeeds. NFSv3 answers this with a write verifier, a token that changes with each boot and that the client compares; this protocol has none.
- *G7.* A request of several steps can fail after some of them took effect, with an errno that reads as "not done" (see Outcomes); nothing orders or resends them, since the outcome is "known".
- *G8.* The server process dying mid-request leaves that request partly done: a write past one `pwrite`, a 64 MiB copy, an allocation.
- *G9.* A request the server ends without a reply on a live connection (a read timeout, an undecodable request, a reply that went unread) looks to the client like a lost reply; it waits for a newer connection that does not come while this one lives, and fails after the offline timeout.

**Outside the model.** Everything above is about one session. A new session (the old one dropped with nothing of it left, the server restarted, a reconnect to an address whose server never knew it, the client restarted) starts from nothing: the client reopens its handles by path, and a file unlinked while open cannot be reopened. Only a client's restart can leave the old session's changes running beside the new one's (G1). Server state lives in its memory only and is not replicated. The model trusts the Linux FUSE and writeback behaviour, the server's filesystem, quinn's delivery and tokio's scheduling.

**Tests.** The disconnect grid (`crates/client/tests/disconnect.rs`) stages each request kind at a fixed point against a fault and judges the end state against fault-free runs: `reply_lost` (S2 by M3), `original_late` and `original_running` (S1 by M1), `cancelled` and `cancelled_running` (S1 by M2), and its `Leak` class (S3 at quiescence). `crates/client/tests/roundtrip.rs` covers M2's client side against a server that never answers, a held change given up on, a takeover and a failed handshake; `crates/client/tests/mount.rs` pins M5's writeback outcomes through an outage. `roundtrip.rs` also stages the fixed G1, G4 and G5: a dropped session whose change still runs resumed, an orphan release and the release of a reopen's handle held behind the open they may race, and a release that timed out sent again on its connection. None of the tests stages G2 or G6 through G9, nor an interleaving the grid does not hold a request at; the grid samples interleavings, it does not explore them. `spec/session.qnt` is a Quint model of this section: one client's sessions, with S4, liveness, reads and the handshake's internals left out. `scripts/spec/check.sh` checks it: S1, S2, S3, the handle identity, that no owed release waits for a later connection, the attachment counts and the pool count hold in every reachable state of an instance of two calls, three requests and two connections, which TLC explores completely, and so does S1 across one client's sessions. Each fix of a gap the model once pinned (G1's dropped sessions, G3, G4, G5) is a mutation TLC must catch (`spec/README.md`). `scripts/spec/traces.sh` replays what the grid and the roundtrip tests against a real server did, recorded at both ends, against the model: each event must be an action the model can take then, and what the code saw (a change held or not, a cancel's verdict, the attachment's counts) must be what the model says.

## Timeouts

| Where | What | Default |
|---|---|---|
| client | one operation waiting for a connection, and an outage before every operation fails at once | 15 s (`--offline-timeout`) |
| client | one exchange on a live connection, a change's wait for the server to answer the connection's earlier cancels included | none (`--op-timeout`) |
| client | one connection attempt, per resolved address | 10 s (`--connect-timeout`) |
| both | QUIC idle timeout | 10 s |
| client | keep-alive interval | 3 s |
| client | reconnect backoff | 100 ms → 5 s |
| server | hello after connect | 10 s |
| server | reading one request | 30 s |
| server | writing one reply | 30 s, then the stream is reset |
| server | writing one event batch | 30 s, then the connection is closed |
| server | detached session grace (a session with work still running is resumed past it) | 60 s |
| server | a change held behind the earlier connections' changes or those given up on | none: until those finish, or its caller or connection goes |
| server | reading a request stream to its end after the reply | 2 s |

`FUSE_INTERRUPT` is honoured: the vendored fuser dispatches it to the backend (upstream answers it with `ENOSYS`, which the kernel takes as "never" and after which not even `SIGKILL` frees a blocked process), the backend finds the task answering that request in its in-flight table, and only a pending signal makes it abandon the call it is waiting on, with `EINTR`. The kernel queues an interrupt whenever the thread blocked in a request has a signal pending by its reckoning, which counts task work too (`TIF_NOTIFY_SIGNAL`): an io_uring completion delivered to the thread that submitted it, the suspend and cgroup freezers, a tracer's stop. So the backend reads the thread's pending and blocked signal sets from `/proc/<tid>/status` (the FUSE header's pid is a thread id) and abandons the call if a signal the thread has not blocked is pending, or if the thread is an io_uring worker (`PF_IO_WORKER` in `/proc/<tid>/stat`), which io_uring stops (a cancellation, a linked timeout, the ring's teardown) with that very notification. Otherwise the call goes on, and because the kernel sends no second interrupt for a request, the task answering it looks for a real signal every 50 ms and abandons the call when one turns up. The session thread only finds the request; every verdict is read on the blocking pool, never on the session thread or the runtime's one worker. A read of `status` or `stat` holds the caller's memory for its length, and while the caller waits in our request its own hold keeps ours from being the last; but the reply can land while the caller is being judged, and if its process then exits (a fatal signal is what makes that likely here), dropping our hold unmaps its files, whose release on this mount (under the writeback cache) waits on writeback or a `SETATTR` that only those two threads can carry. A verdict waits for a blocking thread when all 512 are busy, and one stuck in such a release holds its thread until its writeback is answered or the mount is aborted. An interrupt that cannot be judged (a caller outside this process's pid namespace, an unreadable status, or a `/proc` that is not this process's pid namespace's, which is checked at mount) is honoured, with a warning. The client's perf report counts the interrupts received for requests still being answered and those that stood for no signal, whether or not a real signal ended the call later. A signal sent to the whole process counts as the blocked thread's although another thread may take it, since `/proc` does not say which will. A real signal's `EINTR` is returned verbatim (`SA_RESTART` cannot restart it), so a program with a signal handler can see `EINTR` from a slow call where a local filesystem would have hidden the signal; after an interrupt the process waits in the kernel's killable sleep until the call ends, so it is killable only through the backend's reply. The kernel's writeback requests are background requests and are never interrupted, so against a server that is alive but never answers, dirty pages stay pending and an unmount blocks in its final sync. A second `SIGINT`/`SIGTERM` to the client during the unmount aborts the FUSE connection through its control file (`/sys/fs/fuse/connections/<minor>/abort`, owned by the mounting user), which fails every pending request with `ECONNABORTED`, releases the processes blocked in them, and lets the unmount complete. Killing the client daemon fails every pending and future call with `ENOTCONN` immediately, and `fusermount3 -uz` detaches the mount point.

## Instrumentation

Every request is accounted for at two levels on the client and one on the server, always, at the cost of a few uncontended mutex locks per request (and on the server a few small allocations, for its entry in the stall table and the paths it names); the tables are logged on `SIGUSR1` or every `--perf-interval`, and each report starts a new window. A per-request trace line with the same fields is emitted under the `jackalopefs_client::perf` and `jackalopefs_server::perf` targets when those are enabled at `trace`. Lines about a request carry the session, the connection key and the QUIC stream id, and the client's its generation too. The connection key is 8 bytes of the connection's TLS keying material (RFC 5705, label `jackalopefs conn id`), the same at both ends and different for every connection, so a client's line and the server's about one request join on (connection, stream) across reconnects and server restarts, which session ids and stream ids alone do not survive; both ends log it when the connection is made. A `RUST_LOG` that does not parse is reported at startup and replaced by `info`. `SIGUSR2` does nothing but say so, since its default action would end the process.

**Slowpath events.** Some events are counted every time they happen, as bcachefs counts its events, and each report has one `perf events` line of `name=window/total` for those that happened in the window, the total since the process started. Each also has a detail, which says what happened to which request and why, with the identifiers that join it to other lines (session, stream, kernel request, operation); it is built only while a tap selects that event (the control socket, below) or the side's event target, `jackalopefs_client::event` or `jackalopefs_server::event`, is logged at `debug`, so it costs nothing until someone looks. `RUST_LOG` enables all of a side's events at once (and `jackalopefs_client=debug` includes them); a single event is picked through a tap. Client: `interrupt` and `interrupt_ignored` (a `FUSE_INTERRUPT` for a request still being answered, and one that stood for no signal; "Timeouts"), `call_not_sent` (the request did not reach the connection: no stream could be opened, or writing it failed; the call waits for the next connection), `call_lost_retried`, `alias_stale` (the path to a node led to another file), `file_dropped_from_kernel` (another client changed a file, and the kernel's copy was dropped), `handles_reported` (the server said this client holds many handles, and the client logged what holds them) and `readahead_limited` (a heavy sequential read waited on reads the readahead window sized; "Readahead warnings"). Server: `request_cancelled` (the client ended or reset a request stream before the request was complete, or gave up on a change before it began, which was dropped unrun), `request_stream_failed` (any other failure before the request was read, usually the connection's), `request_read_timeout`, `request_held` (a change waited for changes still running that the client gave up on or that came from the session's earlier connections), `request_abandoned` (the client gave up on a change already running, and the session's later changes wait for it), `request_superseded` (a change from a connection its session has since resumed elsewhere, dropped unrun), `reply_undelivered`, `reply_stalled`, and the watch table's (Change notification).

**Stalls.** The tables describe requests that finished; a request that never does would show only as the in-flight gauge. So both sides keep every request being answered in a table (the client's is the one interrupts are routed through) and a watchdog thread looks at it once a second: a request in flight 5 s is reported at `warn`, and again at 10 s, 20 s, 40 s and so on, and one that was reported gets a `stall ended` line at the next check when it ends (the client's with its total and errno, the server's with its total and the phase it ended in). The watchdog is an OS thread of its own, so it still runs when the tokio runtime is what is stuck, and it waits at most 200 ms for the in-flight table's lock and each request's own, so a deadlock on them is reported (as a lock held too long) rather than silencing it, and as long for the client's reads naming callers (below); a check that panics is logged and the next one runs. It logs like everything else, so an output that blocks (a terminal no one reads) stops it too. When many requests stall together, the oldest eight are described one per line and the rest counted by operation and phase, and likewise for the ones that end. A report lists every request in flight at least a second the same way.

Some hangs leave nothing in the table, so the watchdog also reports, on the same schedule and with the same summary, conditions that persist: on both sides, a tokio runtime (with its one worker, the network thread) that has not run the task it gives it every second for 2 s or more (on the server that leaves new requests unread, so they never enter the table); on the client, a FUSE session thread that is away from its read on `/dev/fuse` while no request completes (blocked in a handler, with every request behind it waiting in the kernel), and an invalidation call that does not return.

A client stall line names the kernel operation, node, handle, offset and size, the thread blocked in it and its process (from `/proc/<tid>/status`, never `cmdline` or anything else that takes the target's mmap lock; not looked up when `/proc` is another pid namespace's; read on a thread the watchdog starts for the check and waits on at most 200 ms, or for the in-flight lines of a report on the blocking pool, unwaited, so the main thread stays free to abort the mount), and where the request's call to the server stands: `waiting for a connection`, `waiting for the server to answer a cancel of an earlier change` (a change, behind one the connection gave up on), `opening a stream` (the server's limit of 1024 concurrent streams holds a call here while others are outstanding), `sending` (flow control), or `awaiting the reply`, with the paths and handles the call names, the connection generation and key, the QUIC stream id and the attempt; or that the request's task has not run at all. These reads can be caught in a release on this mount too, and more readily than an interrupt's verdict: a readahead names the thread whose read started it, which is not blocked in the request and can exit at any time, any exit at all. A read caught that way leaves that check's remaining callers unnamed (said so in their lines) while the watchdog goes on reporting, and the report's in-flight lines go missing; unmount waits for the read as for any release on the mount, until it returns or the second signal's abort frees it. A summary line follows, with what tells the stuck component apart: the kernel's `waiting` count; how many requests were answered since the last check and how long ago the last one was (one stuck request among flowing ones, or everything stopped); how long ago the runtime last ran a task the watchdog gives it every second (a wedged runtime makes every call look like it waits on the server); the FUSE session thread's state and kernel wait channel (`fuse_dev_do_read` when it is idle, waiting for the kernel's next request); the connection; and what the invalidation thread is doing (which notifier call, on which inode), whose notifier calls are blocking writes to `/dev/fuse` that wait on kernel locks. The session thread ending without this client unmounting, which leaves the mount answering nothing, is reported once. Thread states are not read when `/proc` is another pid namespace's.

A server stall line names the session, the connection key and the QUIC stream id (the same numbers the client prints, so the two sides' lines can be joined), the operation and the paths or handles it names, and its phase: `reading the request`, `held behind changes given up on or from the session's earlier connections` (Sessions and resumption), `waiting for a blocking thread`, `watching its directories` (change notification, below), `in the filesystem` or `sending the reply`. For one watching its directories or in the filesystem it adds the blocking thread's state and kernel wait channel, which says where the call is stuck. Its summary line carries the requests answered since the last check and the runtime's heartbeat.

**Control socket and `jackalopefs-ctl`.** Each process serves a Linux abstract Unix socket, `jackalopefs/{uid}/{client|server}-{pid}`, so there is no file to create, protect or leave behind; only its own user and root may use it, checked by the peer's credentials, and it is served from a thread and runtime of its own, so it answers while the process's runtime is the thing that is stuck. The protocol is Cap'n Proto in the wire protocol's framing, on a schema of its own (`crates/proto/schema/control.capnp`) with its own revision, which every request carries and the process checks. A reader asks for counters or for the handles open, as often as it likes, or subscribes once: the counters are the process's resource use, the handles it holds open by kind, every event's count and every operation's totals since the process started (count, bytes, items, errors, total time, and latency and size histograms; the client's at both the `fuse` and `call` levels, the server's at `request`), which never reset, so any number of readers take differences of their own; a subscription selects events by name and request summaries by operation (each the fields of the per-request trace line, with its identifiers), and lasts until the reader goes, which ends it at once. A subscription's queue holds 1024 records and 32 MiB at most; what does not fit is dropped, and the reader told how many with the next record that fits, and in a capture's census. While nobody subscribes, an event costs a relaxed load and the log filter's cached check of its call site, and a request a relaxed load or two. The socket's name can be taken by anyone, abstract names having no permissions, so `jackalopefs-ctl` checks the credentials of what it connects to: the user it runs as, or root, and the process the name says. `jackalopefs-ctl list` shows this user's processes, `top` redraws their resource use (below), their operations' rates, bandwidth, median size, latency mean, median and 99th percentile, and errors, and their events' rates every interval, `counters` prints the raw totals for scripts, `handles` lists the handles open, and `trace` prints events and requests as they happen; it finds the sockets through `/proc/net/unix`.

**Who holds the handles.** A client records with each handle the process whose open made it: the FUSE header names the calling thread, and the open's task reads that thread's process id and name from `/proc/<tid>/status` and the process's `comm` (never `cmdline`, as for the stall line) on the blocking pool before it calls the server, not on the FUSE session thread or the runtime's one worker, which two blocking reads per open would hold up. What it finds for a thread is kept for 100 ms, failures included, so a walker opening thousands of directories from a few threads costs a few reads; one open from each of many short-lived processes costs one read each (about 30 µs of the client's CPU with the hand-off to the blocking pool, measured). A caller outside the client's pid namespace, or a `/proc` of another namespace's, leaves the handle unattributed. It is the opener, not the holder: a descriptor inherited across `fork` or passed over a socket is still put down to the process that opened it. None of this leaves the client. `jackalopefs-ctl handles` asks the client for one row per opener, its files and directories and the deepest directory holding at least half of them (what a tree walker is walking), and asks a server for one row per session, with its client's address and whether it is attached, detached, or dropped with requests of it still running (M1), whose handles stay open until they end. Either way the rows are grouped on the control socket's own thread, outside the table's lock but for a snapshot of it, and at most the 256 largest are sent.

**Process resources.** What a process spends is read beside what it serves, because overhead per request is invisible in latencies that look fine: `getrusage` gives the CPU time (user and system) and context switches of every thread, exited ones included, and the main runtime's stable metrics give its workers, the wall time they spent running tasks (busy, which counts a task blocked in a syscall or on a lock, so it is not CPU and can exceed it) and how often they parked. `jackalopefs-ctl top` shows them as rates over each interval, timed by the process's own uptime in the two readings, and divides by the requests served at the process's outermost level (the kernel's on a client, the clients' on a server) to give CPU and switches per request and CPU per MiB moved; the periodic report has the same figures over its window as its `perf process` line. Many switches per request mean threads handing work to each other, high CPU per request with low per MiB means per-request overhead rather than bytes, and a lone worker near 100% busy is the network thread saturated. `jackalopefs-ctl counters` prints the raw totals as `key value` lines, which is what `scripts/perf/bench.sh` reads.

**Latency and size histograms.** Each operation's totals also keep two histograms since the process started, of every request's latency and of the bytes moved by those that moved any, in log-linear buckets four to a power of two, so a bucket is at most a quarter wide and a power of two (a 4 KiB read) bounds its own exactly. This is bcachefs's `time_stats` in the shape the rest of the counters have: bcachefs keeps a running mean and deviation, all-time and exponentially weighted, and estimates quantiles opt-in; cumulative bucket counts instead let any reader take exact quantiles over its own interval from the difference of two readings, which is what `top`'s size p50, p50 and p99 columns are. A bucket travels as its upper bound and count, so `jackalopefs-ctl` needs no bucketing of its own and cannot misread a changed scheme. The cost per request is two increments under the lock the totals are already taken under. The latencies are general-purpose; the sizes tell a workload of small requests (a torrent client's partial-page reads) from one of large ones at a glance.

**Frame capture.** A subscription can also ask for the frames themselves: each captured exchange is one record holding the request's body as the client sent it and the server received it (after the client puts owners in server terms, before it rewrites the reply), and the reply's, so the two ends' captures of one exchange are the same bytes and decode with `capnp convert` as they are. One exchange in `--every` is captured, chosen by hashing the connection key with the QUIC stream id: both ends compute it alike, so a capture taken at each end holds the same exchanges, with nothing said between them, and the choice does not fall in step with a workload's own period. An exchange that ends without a reply is captured with why (`abandoned` by the caller, `lost` with its connection, `not sent`, `undelivered`, `stalled`, `superseded` on a connection its session has since resumed on another; a change the caller gave up on as the server answered: `unrun`, `fenced`, `unread` when the server never had the whole request, or with the reply it got after all), and one whose reply does not decode with that reply as it was read (`undecodable`); a request that does not decode is captured as it was read, its first MiB; one batch of change events in `--every` is captured too, counted alike at both ends so both take the same ones. Unless the capture asks for payloads, the data of reads and writes is cut from the frames (they are re-encoded without it, only when captured) and its length kept. `jackalopefs-ctl capture` writes a file, readable by this user alone, that starts with a fixed magic and both protocol revisions, so `dump` refuses a file of another control revision before decoding anything and warns of frames of another wire revision; then a header naming the process and what was selected, the records (the control protocol's own frames), and a census the process takes from the subscription itself when the capture ends: per operation, the exchanges it made or answered while the subscription lasted, those it chose, and those of them dropped, with the records still queued written before it, so a sample can be scaled to the whole. When the process goes away first, the file ends with a census of what it holds. `dump` prints each record with its frames decoded in full. While no subscriber wants frames, an exchange costs one relaxed load more.

**Client, `fuse` table.** One row per kernel operation: the request is counted from the moment the session thread hands it to a task until the reply's `writev` to `/dev/fuse` returns (fuser replies synchronously, and every handler replies last). This is the latency the kernel sees, and it includes directory pages served from the client's own buffer without a server round trip. The trace line carries the request id, the pid that made the request, the node (the server's inode number, except for a file that goes by a substitute; "Node table"), handle, offset and size, so a storm can be attributed to a process and a per-file sequence read off. Not counted: `forget`, which has no reply; requests refused before a task is spawned (a name too long, a non-zero xattr position); and the reopens the connection manager makes after a lost session, which are not requests from the kernel and bypass the call table too (the reconnect is logged at `info` with the handle count).

**Client, `call` table.** One row per server request, its trace line carrying the id of the kernel request it serves (a task-local set by the FUSE layer; an orphan handle release made after a timed-out or interrupted open has none), with four phases: `wait` (for a usable connection, and for a change, for the server to answer the connection's earlier cancels), `open` (the bidi stream), `send` (the request frame and finish), and `reply` (finish to decoded reply: the round trip plus the server's work). A phase still in progress when a deadline passes or an interrupt arrives is charged up to that moment, so a timeout or an `EINTR` shows where it was spent. A call that was resent after a lost connection is counted in every column except the phase means, which cover only single-attempt calls, so a few reconnects cannot dominate `wait`; the `retried` count says how many were left out. The report ends with the kernel's `waiting` count for the mount (requests queued for the daemon, from `/sys/fs/fuse/connections`) and the connection's QUIC statistics: round-trip time, congestion window and MTU as they stand, and packets lost, congestion events and bytes each way since that connection was made, with the connection generation so a reconnect's reset is visible.

**Server table.** One row per request with its phases: `read` (stream accepted to request decoded), `held` (a change held behind those still running that the client gave up on or that came from the session's earlier connections; zero for every other request, and not a column of the report's table), `wait` (`spawn_blocking` called to the closure running, non-zero only when the blocking pool is saturated), `op` (the filesystem work) and `send` (the reply frame and finish). The client's `reply` phase less the server's total is the network's share. The server's report ends with one line per attached session giving its connection's QUIC statistics (the client's fields, keyed by session and remote address), and the same line is logged when a session's connection ends, so the totals since connect are not lost with it; since the server is the sending side of every read, its congestion window and losses are what bound a download, and the client's own window says nothing about one.

**The link and the verdict.** Both reports end with what the host itself can say about the link, the evidence before the verdict drawn from it. One line per physical port (the interfaces under `/sys/class/net` backed by a bus device, so bridges, bonds, VLANs, veths and loopback are left out because their counters and speeds describe nothing physical): bytes per second each way over the window, the speed sysfs reports, the utilization of that speed for a wired port, and the packets the port dropped or missed over the window by counter. One line for the host's UDP socket drop counters from `/proc/net/snmp`, since a socket receive buffer that overflows is where a receiver that cannot keep up loses packets. Each connection's QUIC line carries its own rates and losses over the window. Then a verdict, only when the busiest wired port is at 80 percent of its speed or more: if this connection is under half of that port's traffic in the same direction, "bandwidth-starved by other traffic on the link"; otherwise "the link is full with this connection's own traffic". The verdict names the port, the direction, the utilization and the share, so it can be checked against the lines above it. It assumes the connection runs over that port; a share the connection could not have on it (more than the port moved) means it runs elsewhere, and there is no verdict. The share reads a few percent low because the port counts link-layer bytes and the connection counts UDP payload. A wireless port gets no verdict: its speed is the negotiated PHY rate, not a capacity, and the airtime other stations take is invisible to it. Rates need a window of at least a second; a report sooner than that keeps the previous rate baseline, so reports closer together than a second still get rates every so often, while drops are counted per report. Ports are enumerated on every report, so one that appears or comes back is metered from then on. Left out on purpose: a queueing-delay signal from the round-trip time (one smoothed sample per window against a floor that a reconnect resets exactly when it matters) and ECN (quinn exposes no counter for it, and a home switch does not mark). The `min` column on the per-op rows, against `mean`, is the queueing signal that is kept.

**Columns.** `n`, `conc` (the row's summed latency divided by the window length: the mean number of that operation in flight, which is the number that says whether a copy is pipelined), `min`, `mean` and `max` latency, `bytes` (payload: read replies and write data; a `copy_file_range` moves no payload, so the client's call row counts nothing for it, while its kernel-level row and the server's row count the bytes the server copied), `items` (directory entries returned), `errno` (failures by the errno the caller saw, so a lookup storm that misses reads as `2xN`). A report resets every count; the in-flight gauge is not reset and its peak restarts from the current value. An operation that began before the report lands wholly in the new window, which can push `conc` above the truth for windows much shorter than the operations in them. The `write` rows describe the kernel's writeback, not the application's `write(2)` calls, which return from the page cache.

**What the kernel granted.** `init` asks for 1 MiB of `max_write` and `max_readahead` and 64 background requests, but the kernel proposes its own readahead (the mount's `bdi` setting, 128 KiB by default) and only lets the daemon lower it, so every read the kernel makes through its page cache is bounded by that, whatever `MAX_IO` says (per file: the window is taken when the file is opened, and `POSIX_FADV_SEQUENTIAL` doubles it). An `O_DIRECT` read bypasses the page cache and comes at its caller's size, up to the request cap of 1 MiB that fuser negotiates (`max_pages`). The values as granted are read after mounting, with the device minor taken from `/proc/self/mountinfo` so that no request goes through the mount to learn it, from `/sys/class/bdi/0:<minor>/read_ahead_kb` and `/sys/fs/fuse/connections/<minor>/{max_background,congestion_threshold}` and logged at `info`.

**Readahead warnings.** Every FUSE mount gets a fresh bdi at the kernel's 128 KiB, and a sequential reader through the page cache then has one or two reads of that size in flight, each a round trip to the server, however fast the link is. Only root can raise it, through sysfs, and the setting lasts until unmount and applies to files opened after it. So at mount, when the window is below 1 MiB, the client warns with the command for this mount and a form for every mount (`$(mountpoint -d <mnt>)`); it suggests 4096 KiB, room for several full-size requests in flight. While mounted it watches for the case where the window turns out to be the limit (`readahead.rs`): per open file, as the kernel keeps its readahead state, a run of reads each starting within 2 MiB of where the run has reached (the kernel's synchronous and asynchronous reads arrive slightly out of order). A run is reported once, when it has read 256 MiB (a heavy read, not a preview or a header scan), its largest read is at least 64 KiB and below the 1 MiB request cap (readahead's reads grow to the window within a few, while the writeback cache filling pages for an unaligned rewrite asks for a page or a small folio at a time; a read at the cap means the window was not what sized them), and a read was in flight 90% of its time or more: in steady readahead that share is about the read latency over the longer of that and the reader's own time per window, so near 1 the reader is waiting on the window. Reads with `O_DIRECT` (sized by their caller) and on write-only files (the kernel filling a page a write only partly covers) are not counted, and a read's clock starts on the session thread, so time waiting for the runtime counts as in flight. The warning names the reader and the file, the rate, read size and mean latency against the connection's round trip (a latency far above it is the link or the server, which a larger window does not help), and re-reads the setting: when it is already raised, it says the file was opened before that, or sizes its own reads (`POSIX_FADV_RANDOM`), instead of repeating the command. It is logged the first time and at each doubling of the count; each one is the `readahead_limited` event, whose detail (`jackalopefs-ctl trace readahead_limited`) has the file and the numbers. A link or a server that is slow looks the same to this test, reads always out and sized by the window, which is why the latency is shown against the round trip. Not caught: a sequential read spread over many smaller files, since a short run is dominated by readahead's own ramp-up.

## Security

The server's certificate authenticates the server to a client that pins its fingerprint. Nothing authenticates the client unless `--token` is set. The client sends the host it was given as the TLS server name; the certificate is checked only against the pinned fingerprint, never against that name. The default listen address is loopback; a routable address without a token gives every host that can reach it read/write access to the export as the server user. `--allow-other` on the client extends the same access to every local user of the client machine. Which owners cross is the server's decision, and how they are shown the client's ("Ownership"). The server's default, `--ids flatten`, keeps other users' ids on the server and refuses to give files to them; `--ids direct` on a server running as root lets any client chown anything to anyone. The server tells any peer that reaches it, before authentication, which protocol revision it speaks; that is derivable from any build and the ALPN already names the software, and it lets an operator with a valid token see a mismatch for what it is.

**Ownership.** Each side has an `--ids` mode, and the `Ack` of every hello carries the uid and gid the server runs as. The server's mode is policy it enforces whatever the client does; the client's is presentation. A server with `--ids direct` sends every owner as its filesystem has it and applies whatever ids a client asks for, as far as its privileges allow. With `--ids flatten`, the default, only its own uid and gid cross: every other owner goes out as nobody (65534), and a `setattr` or POSIX ACL naming another id, nobody included (a chown copied from what was shown must not overwrite the owner it hid), is refused with `EPERM` before anything is touched; an ACL that does not parse is refused with `EINVAL`, since an honest client's kernel encodes every ACL itself, and every other `system.*` attribute is neither read, set nor removed (`EOPNOTSUPP`): that namespace holds the other ACL formats (NFSv4, richacl, CIFS), whose principals the server cannot read, and nothing a client needs. A flattening server refuses to start as uid or gid 65534, where nobody would be indistinguishable from its own. A client with `--ids direct` shows owners as they come and sends ids as given; with `--ids owned`, the default, it shows the server's uid and gid as its own effective ones and every other owner as nobody, and a chown or ACL naming anything but its own ids fails with `EINVAL` before it is sent, which is what `chown(2)` says of an id with no mapping in a user namespace (under `--default-permissions` the kernel refuses a chown to another user with `EPERM` first). It warns when nobody is on either side of that mapping, or when the server runs as root, whose files would all show as the user's. Both sides map attributes in every reply and the named-user and named-group entries of `system.posix_acl_access` and `system.posix_acl_default`, which the client's kernel converts to and from that extended attribute form. The client maps where replies come in and requests go out, against the ids of the connection that carries them, so a server restarted as another user is described by its own ids from its first reply; what the kernel cached under the previous ids lasts until the post-reconnect sweep or the attribute TTL. The server checks every access as itself regardless, so a mapping can make `--default-permissions` stricter than the server, never looser. `flatten` does not make a server running as root safe: its own ids are root's, so a client may still take any file as root, set setuid bits, and write `security.capability` (whose version 3 carries a uid of its own, which is not mapped) or `trusted.*` attributes. `direct` on both sides is the configuration the validation suites run (`docs/validation.md`); `flatten` and `owned` are for a user mounting their own files from another machine.

Each process's control socket (Instrumentation) is open to its own user and root only, by the peer's credentials; what it gives (paths, file names, timings, and with a capture's payloads file contents) is what that user can see anyway. A capture file holds names and paths, and file contents when asked for, and is created readable by its user alone. The handshake's frames, which carry the token, are never captured.

## Known limitations

- Mount points inside the export are not exported (`RESOLVE_NO_XDEV`). Subvolumes and snapshots of the export's own filesystem are, their files going by substitute inode numbers ("Node table").
- The export's filesystem must give file handles (`name_to_handle_at`); with `AT_HANDLE_FID`, Linux 6.5, every one does, and before that the ones that can be exported over NFS. A server refuses any other. It trusts the handles to tell files apart: a filesystem that sets no inode generation cannot tell a recycled inode number from the file that had it before. Handles on FUSE last as long as the daemon's mount, and overlayfs gives a file a new one when it is copied up, so on those a file can turn into a new one under the client (the server warns at start-up).
- A substitute inode number is 64 bits wide, so a 32-bit program built without large-file support gets `EOVERFLOW` for a file outside the root's subvolume.
- Every listing carries attributes, so the server describes every entry it lists: measured on loopback, about 5 µs of server time and 176 bytes on the wire per entry, against about 0.4 µs and 40 bytes for a bare name. A directory of a few thousand entries does not notice; a listing of 100 000 that never stats (`find`, `ls -f`) took 0.6 s where a bare listing took 0.1 s, while one that stats every entry (`ls -l`, 3 s) costs the same as before. The two file handle calls are about half of an entry's cost, the xattr names a third, the `statx` the rest.
- A directory the server can read but not search (mode `r--` for it) lists as empty, the dots aside: a listing carries only entries the server can describe, and describing one needs search permission. POSIX lets such a directory list its names.
- `name_to_handle_at` on the mount itself gives handles that last as long as the client process, FUSE's being made of the node id.
- `PATH_MAX` (4096 bytes) bounds the depth of the exported tree, because the whole relative path is resolved in one `openat2`.
- A directory rename racing a lookup inside that directory can produce a spurious `ENOENT`; the kernel does not serialise the two and path-based addressing cannot close the window. The same is true of sshfs.
- The notice that a directory was dropped from the watch limit can overtake, on the network, a reply sent from that directory just before, which the client then caches unwatched until the TTL: replies and events travel on separate streams, and the directory is held only until the reply is written.
- A restarted server watches only the root at first, so what a client's kernel still caches beyond the entries its post-reconnect sweep drops (4096) is left to the TTL until a request names its directory.
- `RUST_LOG` turns on all of a side's events at once (`jackalopefs_client::event=debug`); one event alone is picked through `jackalopefs-ctl trace`. Captures hold request and reply frames and batches of change events, not the handshake's.
- Control socket names are abstract, so they belong to a network namespace while the pids in them belong to a pid namespace: in containers that share a network but not their pids, two processes can claim one name, and `jackalopefs-ctl` refuses the one whose pid does not match.
- inotify reports a change to the directory of the name it was made through, so a change to a hardlinked file through a name in a directory the server does not watch is left to the TTL; so is a change to the attributes of a directory the kernel still caches after its parent was dropped from the watch limit, when something holds the directory itself (a process's working directory).
- Events are lost during a disconnect (covered by the post-reconnect invalidation and the TTL); inotify does not report `mmap` writes; a directory the server cannot read, and everything below it, is never watched; the event stream is ordered relative to itself but not relative to replies, so a reply can briefly re-cache what an event just invalidated. The TTL is the correctness backstop in all of these cases.
- A write's failure surfaces at `fsync(2)` or `close(2)`, as `EIO` (`ENOSPC` as itself) at close, not at the `write(2)` that cached it; a server that vanishes takes the pages not yet flushed with it, except those the reconnect retry delivers. Writeback attempted once an outage is past its deadline fails at once like every other call, so those pages are lost even if the connection returns moments later: the kernel does not retry writeback that failed, and keeps the pages clean in its cache, so they reach the server only if dirtied again before anything reopens the file (until then, readers on this client see data the server never got). Letting writeback wait would block `close(2)` for the full deadline again. `crates/client/tests/mount.rs` pins this, and the writeback that waits through a shorter outage.
- A regular file this client holds open keeps the size and mtime the kernel has for it until it is closed, whatever changes on the server; the kernel trusts its own cache for a file it holds. After the close, a file this client wrote is looked up afresh on the next access, and a file it only read is dropped by the first attribute refresh that sees a change. A file nobody holds open is seen afresh within the attribute TTL plus one access. The mtime of a file written through the mount can be the time the server received the data rather than the time of the `write(2)`.
- `O_APPEND` is positioned by this client's kernel, so two clients appending to one file overwrite each other's data rather than interleaving. A file writable but not readable (mode `0222`) cannot be opened for writing through the mount unless the server runs as root.
- Each process does its networking on one core: about 20,000 small requests a second on loopback, shared by every client of a server. QUIC work for one connection is serial in quinn whatever the thread count, so the way past this is a runtime per connection (quinn's `Runtime` decides where a connection's driver runs) for many clients, and several connections per client for one heavy client, not more workers; `TOKIO_WORKER_THREADS` raises the worker count meanwhile.
- With one worker, stdout that blocks (a stopped terminal, a full pipe) stops all networking at the next log line, not only the tasks that log.
- A write that does not cover whole pages, into a file that already has data there or is sized past it, costs a 4 KiB read round trip for each partial page the kernel does not have cached: the writeback cache must fill a page before writing into part of it. Torrent clients do this all the time, since a multi-file torrent's 16 KiB blocks are not page-aligned within each file.
- One session can hold the server's whole handle pool and starve every other: the share only reports it. With it the costs that grow with a client's handle table grow without that bound too: the client scans its whole table for an inode's writers and live handles (on an attribute change, a writer's release, an invalidation, `SEEK_DATA`), a client whose session was lost must reopen every handle within `--offline-timeout`, and every open directory holds an inotify watch outside the watch limit.
- Multiple clients: cache coherence between them is best-effort (push invalidation plus TTL), and locks are local to each client.
- Any real signal, not only a fatal one, interrupts a blocked call with `EINTR` (see Timeouts); and the kernel's writeback is not interruptible, so cached writes against a server that is alive but never answers are pinned until the mount is aborted.
- A thread blocked in a call gets its io_uring completions late. The kernel runs the task work that posts them when the call returns, and the daemon cannot ask for the transparent restart a local filesystem uses (FUSE takes no `ERESTARTSYS` in a reply, and a restart would repeat a request the server may have carried out), so another thread waiting on the ring sees the completion only when the call ends: measured, 200 ms instead of 20 against a server paused for 200 ms. After such a notification the call waits in the kernel's killable sleep (state `D`) until it ends, and a real signal ends it within 50 ms. When another thread of a multi-threaded process takes a Ctrl-Z, the blocked thread usually stops only once the server replies, and a system suspend against a stalled live connection can time out freezing such a thread.
- A change the caller abandoned (a signal, `--op-timeout`) that was already running still finishes on the server, so its `EINTR` or `ETIMEDOUT` means it may have happened: a write (up to 1 MiB of it), a `copy_file_range` (up to 64 MiB; `docs/copy-file-range.md`), a punch or zero (`docs/sparse-files.md`), a truncate, a namespace or xattr change. It cannot land after the session's later changes, which wait for it, whether the connection lives or the session resumes; but a session that cannot be resumed is not ordered: one whose client restarted or remounted, one on another server. Only changes are ordered. A read or `fsync` after an abandoned change, or on a resumed connection, can see the state from before it, and since that change is the session's own, no event corrects what the client then caches until its TTL runs out. A change stuck on the server holds every later change of the session until it finishes, past the session's grace too, since a session is resumed for as long as any of its work runs (only a remount gets past it), and each of those later changes can be interrupted; and a server whose connection lives but which never answers a cancel (a server bug) holds them for as long as the connection lasts; the stall watchdog names that wait. An open given up on keeps no descriptor, since its orphan release waits for it, though one already under way has created or truncated its file. The kernel's release is not ordered, so one can overtake a write on its handle that has not yet found the handle, which then fails with `EBADF`; only a write the kernel was already answered for can be in that position. A writeback write given up on (`--op-timeout`) before it began is dropped and never runs, and since the kernel does not retry failed writeback, its data never reaches the server. `crates/client/tests/disconnect.rs` shows each case.
- `lseek` with `SEEK_DATA` or `SEEK_HOLE` fails with `EINVAL` on a file this client has open for writing, because the kernel may hold data the server has not seen and the server's answer would call it a hole; callers fall back to reading the file (`docs/sparse-files.md`). Otherwise the answer is the server's filesystem's, as stale as a read can be.
- `fallocate` is the server's filesystem's: where the export's filesystem has none, the caller gets its `EOPNOTSUPP`, and glibc's `posix_fallocate` then writes into every block, over the network. A long range is several requests (64 MiB each), so a failure or an interrupt part-way leaves the part before it done, and the request in hand finishes on the server as an abandoned copy does.
- Device nodes are refused with `EPERM` before reaching the kernel; `chown` to other users needs a privilege the server does not have and fails with the kernel's errno, or with `EPERM` from a flattening server and `EINVAL` from an owned mount before that ("Ownership"); `RENAME_WHITEOUT` is refused with `EINVAL`.
- `flatten` and `owned` show only the server's user ("Ownership"; `direct` on both sides is the way out of all of this). A file owned by a group the server's user is in only as a supplementary group shows as nobody's, so `--default-permissions` checks the other bits and may refuse what the server would allow, and a chgrp to such a group is refused (`rsync -a` run as an ordinary user exits 23 over it). Under `--default-permissions` the local kernel strips setgid from a `chmod` of a file whose group shows as nobody's (the caller is not in it), and the server applies the stripped mode. Tools that write a new file and rename it over the old one (`sed -i`, editors) copy the old group with `fchown`, which fails for a group that shows as nobody's, so the new file keeps the server's group. An ACL naming another user cannot be edited through the mount, and `getfacl` shows each such entry as nobody, several times over if there are several. An owned mount run as root shows the server user's files as root's, and one of a server running as root, where both hosts give the user the same uid, shows the user's own files as nobody's.
- A negative lookup is not cached, so a directory walker probing every directory for a name that is not there costs one round trip per directory. It cannot be cached coherently yet: the kernel's entry invalidation (Linux 7.0 and later, through its removal API) refuses a dentry with no inode, so a cached absence could not be dropped when the name appeared elsewhere, and fuser 0.18 neither reports that refusal (it maps the kernel's `ENOENT` to success) nor exposes `FUSE_NOTIFY_INC_EPOCH`, the whole-cache invalidation that would.
- An extended attribute set on the export directly is, until its event or the attribute TTL, reported absent (`ENODATA`) by a client that had the file's names cached, and every caller treats that as fact; a stale attribute is a wrong number, a stale absence is a wrong existence.
- Metadata operations that reach the server without a handle (xattrs) fail on a file that has been unlinked while open; those with a handle, or for which the client still holds one (stat, chmod, chown, times, truncate, fsync, read, write through the descriptor), work.

## Follow-ups

`FUSE_HANDLE_KILLPRIV_V2`, which would spare the kernel its per-write `security.capability` probe by making the daemon responsible for stripping setuid, setgid and capabilities: our server's kernel does that on its own `pwrite` and `ftruncate` when the server process lacks `CAP_FSETID`, but not when the server runs as root, and fuser 0.18 surfaces the kernel's write flag but not the `O_TRUNC`-open or size-setattr ones, so honouring it would need a schema change; the probe is answered from the metadata cache instead. Negative-entry caching once fuser exposes the epoch notification; a `--no-xattr` mount option answering `GETXATTR`/`LISTXATTR` with `ENOSYS` so the kernel stops asking, for mounts that need no xattrs at all; a general speculative fetch that would subsume `Attr.xattrNames`. Kernel-module backend with fsnotify injection (the FUSEX "mode B" in the research notes); `keep_cache` for reads once something bounds a stale page cache for a file nobody holds open; synthetic ids for foreign devices; `FUSE_COPY_FILE_RANGE_64` for copies of more than 4 GiB per kernel request, which needs a fuser patch and only matters if a server ever copies that much per request (`docs/copy-file-range.md`); server-side locks for multi-client use; richer authentication; raw-payload framing to avoid a copy on large I/O.
