# The session protocol, as a Quint model

`session.qnt` is one client's session with the server as `docs/design.md`'s "Failure model" describes it, written in [Quint](https://quint.sh) so that its invariants are checked for every interleaving of a small instance rather than for the ones the disconnect grid stages. It is step 1 of the recommendation in `docs/research-verification.md`.

## What is modelled

The client's calls (`Caller::attempt`, `client::exchange`, the open and release paths), its connections by generation with `Attached::cancels`, its handle table with the releases owed, and its own traffic: reopens after a new session and owed releases (an open's of unknown outcome, an orphan, among them), each ordered and counted on `cancels` when given up on. The server's sessions with their epochs and the counts `running`, `abandoned` and `running_older`, each request from decode through hold, begin and finish with the verdict on a cancel, and each session's `Handles` and the shared pool. The faults: either end losing a connection, the client's give-up, resends, a resume, a takeover, a resume handshake lost after the server resumed, a session dropped while its old connection's requests go on, a request outliving its connection at the server (one read whole before the connection went is still decoded, may drain and begin, until its task notices), and filesystem work failing with an errno. Every action's comment names the code it stands for.

Several sessions exist in the model, since a session dropped with nothing of it left is followed by a new one, while one dropped with a request still under way is resumed; the client holds one at a time. Left out, on purpose: S4 (writeback and durability, a separate model when wanted), liveness, reads and `fsync` (no invariant in scope mentions them; releases stand in for unordered requests), the handshake's internals beyond the lost-Ack case, other clients' sessions (G2), partial requests (G7, G8), G9, file contents, the pool running out, and the kernel releasing a handle a reopen killed (a no-op at the server).

The model is of the code as it is; nothing is switched off. It was first written with the gaps `design.md` then listed (G1, G3, G4, G5) still in the code, each pinned by a plain form of its invariant that TLC had to find violated; each fix changed the code and the model the same way, its invariant moved to the ones that must hold, and the behaviour it replaced became a mutation below. A gap found later goes in the same way: the invariant stated with an allowance for it, which must hold, and without, which must fail with its trace.

| Must hold | What it says |
|---|---|
| `S1` | No overtaking within one session: for changes a and b with b after a, every request of a that ran finished before any request of b began. A ghost flag set by `begin` whenever a request begins out of order, in either direction. |
| `S1strong` | S1 across the client's sessions: a session dropped while something of it lives is resumed, not replaced. A client's restart (G1) is outside a model of one client's lifetime. |
| `S2` | A call's request runs at most twice, the second time only as a resend, and for a change on one session only after the first finished. |
| `S3` | At quiescence, with no release owed, the server's handles for the client's session are exactly the client's live ones. |
| `S3identity` | Whatever the client holds under an id, the server's entry under that id was opened by the call the client accepted it from: an open's handle is never replaced by another file's. |
| `owedNeverStuck` | Once all else is quiet on a live connection, a release owed can go out on it: none waits for a later connection (G5, fixed). S3 holds at quiescence only, which a stuck release would keep out of reach. |
| `countsConsistent` | The attachment's three counts equal what the request phases say, through every resume and takeover. |
| `poolConsistent` | `HandlePool::used` equals the handles every session holds plus the slots of the opens under way that took one. |
| `aliveIsCurrent` | A connection the client still uses carries its session's current epoch (the model's own sanity). |

Reachability is checked too: for each state the model must be able to reach (a fenced change, a superseded one, a resend that ran, a takeover, an orphan release (the owed release of an open of unknown outcome) held behind its open, an orphan release that ran, and quiescence after a reopen, after an owed release, and while holding a handle on a later connection), its negation is an invariant TLC must find violated. A model that drifts into checking nothing fails those.

Three instances, one per file, because the checkers take a file's whole compiled form and Apalache refuses one past 20 MB:

- `session_tiny.qnt` (2 calls, 3 requests, 2 connections): what TLC explores completely. Every witness and every mutation is reachable in it; none needs more than three requests.
- `session_small.qnt` (3 calls, 6 requests, 3 connections): the simulator's instance, and the scenario runs: the disconnect grid's columns (`reply_lost`, `original_late`, `original_running`, `cancelled`, `cancelled_running`), the takeover, a change held behind one given up on, an open given up on while it ran with its orphan release held behind it, one given up on before it began, an orphan release lost with its connection and sent again on the next, the hovering release race, a session dropped twice while a change of it runs and resumed both times, a new session's reopen succeeding, failing, given up on while it runs (the connection published beside it, the release of its handle held behind it), and outlasting the kernel's release of its handle, a resent open answering from its original's handle, an owed release sent on the connection it was owed on and again on the next when that one is lost, a request decoded after the takeover of its connection and refused, and a change held on a connection the server has lost that drains and runs.
- `replay.qnt` (16 calls, 32 requests, 4 connections): what trace validation replays recorded runs on, with `quint test` only; `replay_test.qnt` checks the replay itself.

## Running the checks

```
scripts/spec/check.sh          # typecheck, the scenario runs, and TLC finding every witness: about five minutes, most of it the reopen witness's deep trace
FULL=1 scripts/spec/check.sh   # also TLC over the tiny instance's whole state space, and the simulation: about two and a half hours more
scripts/spec/traces.sh         # trace validation, below: the fault tests recorded and replayed against the model, a few minutes
scripts/spec/mutations.sh      # each mutation below, caught by TLC: about an hour, most of it the uncounted reopen's deep trace
```

They need Node and a JDK. The first run installs Quint 0.33.0 into `spec/node_modules` from the lockfile and downloads Apalache 0.62.1, which carries TLC, into `~/.quint`; the simulator fetches its own evaluator binary. TLC runs with an 8 GB heap and every core, and spills its state queue, tens of gigabytes for the full exploration, into `~/.cache/jackalopefs-spec/tmp` (`XDG_CACHE_HOME` respected), since a tmpfs `/tmp` cannot take it. Every outcome is asserted.

To look at a trace: `spec/node_modules/.bin/quint verify spec/session_tiny.qnt --backend=tlc --invariant=neverReleaseHeld` prints the shortest one there is to that state; `quint run spec/session_small.qnt --invariant=neverReleaseHeld --max-steps=40 --mbt` prints the shortest the simulator finds, with the action taken at each step.

## Keeping it in sync

The model is of the code; when the code changes and the model does not, the checks go on proving things about a protocol nobody runs. Three things keep the two together:

- Every code reference in the model's comments resolves: `crates/server/tests/spec_refs.rs`, part of the workspace's tests, parses the workspace and fails on any backticked name in the model files that is neither the model's own (an identifier its code uses) nor declared in the source: a path, an item written with `::` (a method on that type, a field or variant of it, an item of that module), or a bare name of an item, field or variant, never of a parameter or local. In this file only paths and items written with `::` are checked. Code is written qualified where a bare word would be the model's (`SessionState::drain`, not `drain`).
- Each modelled file says so in its module doc, and the same test checks those are the files the references resolve into. A commit that changes one changes the model too, or its message carries a line starting `Spec:` that says why not (`Spec: unaffected (reason)`, `Spec: follows in "<subject>"`).
- `scripts/spec/drift.sh`, which `check.sh` also prints, lists the commits since the files were marked that changed a modelled file with neither.

None of this sees behaviour change under unchanged names. Trace validation, below, runs the code against the model, and model-based testing has the model drive the server's code.

## Trace validation

`scripts/spec/traces.sh` runs the disconnect grid and the roundtrip tests that fault a real client against a real server (`file_lifecycle`, `session_resumes_after_a_connection_drop`, `an_orphan_release_waits_for_the_open_given_up_on_while_it_ran`, `a_change_held_behind_one_given_up_on_can_be_given_up_on_too`) with the client and server built with `spec-trace`. Each run, the grid's controls included (649 in all), records what both ends did as model events (`crates/perf/src/spec_trace.rs`), in one order, and `spec/replay.qnt` replays every trace against the model with `quint test`: each event must be an action the model can take then, what the code saw must be what the model says, and every invariant must hold at every step. It takes about five minutes; it is not part of `check.sh`, which instead builds the recording and checks the replay itself (`spec/replay_test.qnt`: a recorded trace replays, and the same trace corrupted as a server without the fence, or a client that took a frame it wrote for one never sent, would have recorded it stops at the event that gives it away). The script fails if a test fails while recording or a trace does not replay; a failure names the run and the events around where replay stopped, and `target/spec-traces` keeps every trace (`<run>.log`) and the assembled modules, with quint's output beside each. `REPLAY_ONLY=1` replays the last recording again. A pass says only that the interleavings those runs took are behaviours of the model.

Left out: the tests on a scripted server (`Blackhole`, no server events), on hand-made connections (`connect_raw`, no client events), with a server restart (which the model does not have), and a kernel release of a handle never opened. `replay.qnt`'s instance bounds a trace to 16 modelled calls and 32 requests; a longer one stops where it runs out.

Each event is recorded where it takes effect: the server's under the attachment lock where the model's action reads or moves the counts, the client's ready-to-send events while the connection's count of pending cancels is read, so the recorded order is the order the code decided in. Elsewhere on the client, events of different tasks are ordered only by when they were recorded, which the rules below allow for.

| Event | Recorded at | Replayed as | Checked |
|---|---|---|---|
| `CallStarted` | `Caller::attempt`, first | `start`, a model call per real one; reads and other unmodelled requests, a release of a handle the model never had, and a kernel release of a dead handle (`Stale`) are passed over | |
| `CallReady` | `Caller::attempt`, while it reads the connection's pending cancels as answered | `send` | the call's connection is the model's current one |
| `ReleaseReady` | `send_releases`, likewise | `owedSend` | likewise |
| `Stream` | `client::exchange`, the stream opened and the frame encoded, before it is written | maps the stream to its request; a reopen's `reopenSend` | |
| `Answered`, `CancelAnswered` | `client::exchange` and its background reader | `receive` | the answer is the model's: reply or errno; unrun (`unread` too), fenced or the reply for a cancel; a superseded change is superseded |
| `Failed` | `Caller::attempt` and `client::exchange` | `giveUp`, `reopenGiveUp`; a frame lost or not sent is the loss's | a cancel is counted exactly when the model counts it; a call failing otherwise, or on a dead handle after it was sent, stops replay |
| `ConnLost` | the connection manager seeing it close | `loseClient` | |
| `Published`, `Connected`, `Owed` | the connection manager (`Published` before the connection is handed to calls), `HandleTable::owe_release` | `publish` after a new session | the connection and session are the model's; a release owed is owed or dead in the model |
| `Created`, `Resumed`, `HandshakeFailed`, `Attached` | `Sessions::create`, `Sessions::resume` under the attachment lock, `DetachUnlessAcked`, `handle_connection` | `newSession`, `reconnect`, or `handshakeLost` when the handshake fails before its Ack | the counts after the resume, whether it came back from the dropped sessions, the connection's epoch |
| `ConnEnded`, `SessionDropped`, `SessionClosed` | `DetachOnDrop`, `Sessions::retire`, the session's drop | `loseServer`, `dropSession`, `closeSession` | |
| `Decoded`, `Undecoded` | `SessionState::fencing`, under the lock for a change; `handle_request` for a frame that never decodes | `arrive`; a reset `seeCancel`, a failed stream `dropCut` | a change exactly when the model's request is one, held exactly when the model holds it; a malformed frame stops replay |
| `HeldEnded` | `SessionState::drained` and `SessionState::stopped`, under the lock | `drain`, `dropCut` | drained or superseded as the model's epochs say; the client stopping the stream stops replay |
| `Began`, `Reserved` | `SessionState::begin`, under the lock for a change; `Handles::reserve` | `begin` | running, superseded or cancelled as the model says, the counts after (a change only), the slot taken or kept |
| `Abandoned` | `SessionState::abandon` under the lock | `seeCancel` | unrun, fenced or finished as the model's phase says, the counts after |
| `Finished` | `GuardExchange::drop`, under the lock for a change | `finish` | the counts after (a change only) |

Every exchange the server records must be one the client recorded: a request replay maps to the model's, one the model leaves out (a read), or an attempt nothing of which was sent, of which the server may record only a frame never decoded. Anything else stops replay.

Where the code takes in several steps what the model takes in one, or records on different tasks what the model orders:

- An attempt of which nothing reaches the server (given up on before its frame was written whole, `NotSent`, a dead handle) is never sent in the model; its ready event and `Failed` are passed over. `NotSent` includes a call handed a connection whose loss the manager has seen and not yet published, which the model, with the loss already taken, could not send on.
- The client's loss of a connection is the manager seeing it close. Each exchange on it learns of the loss by itself, before or after; those events are passed over. An answer read on the connection before the manager saw it close, but recorded after, is taken first, a step of its own.
- The server's loss of a connection may first show in a request (`Undecoded` or `HeldEnded` for a failed stream) before the connection's task ends; replay takes `loseServer` then, a step of its own. A request on a connection the server has lost of which the server records nothing more (a frame that came as the connection went) is dropped, a step of its own, once nothing later needs it.
- A cancel's verdict of `lost` has no answer in the model, whose connection loss takes care of it.
- `arrive` holds for any request on a connection the server has lost, as long as it has not been dropped: the model does not tell a frame read whole before the loss from one that was not, so replay accepts a late decode of either.

## Model-based testing

`crates/server/src/mbt/` replays runs of the model against the server's session machine, reading them with `crates/mbt`, which holds what the model-based tests share (the traces, the corpus, the replay and its comparison): the real `Sessions`, each request's `Exchange` with its `GuardExchange`, `Ops::reserve` and `ops::dispatch` on a scratch directory, the handles and the pool. Each server step of the model is what the code does for it: `SessionState::fencing` for `arrive`, `SessionState::drained`, `SessionState::stopped`, `SessionState::abandon`, `SessionState::begin` with the open's `Ops::reserve`, the work and the guard's drop for `finish`, `Sessions::resume` (with the takeover of the connection it supersedes), `Sessions::create`, `Sessions::reap`, the drop of an `AttachmentConn` or a `DetachUnlessAcked`. After every step the code's state must be the model's; a failure names the run, the step and the action, with a diff of the two.

- **Which step.** A trace from `quint test` records no actions, so each step is inferred from what it changed: a request's phase moving the way only one action moves it, the generation, a connection's server end, a session leaving the table, its epoch, its handles closing. Anything else is the client's or the network's, and must leave the server's state alone. A step that fits none, or more than one, stops the run; where the trace names the action (`quint run --mbt`), it must agree.
- **What the driver reads from the model.** What the client, the network and the filesystem did: which requests were written (the origin, the call's kind, the connection), which answers the client read, which end of a connection went, and whether a request's work failed (the action's recorded choice; in a scenario's trace, which records none, the answer it shows, an answer lost or not sent counting as success). Everything the server decides comes from the code: a request's session and epoch are what the code gave its connection, never the model's.
- **What is compared.** Each session's epoch, `running`, `abandoned`, `running_older`, whether it is in the table and detached, whether anything of it is under way (its holders, the model's `alive`), and its handles by the request that opened each (every open opens a file of its own); each connection's session and epoch; the pool; each request's phase, slot and answer. Model requests are real ones: a change is a mkdir, an open opens a file, a release releases, and `Request::changes` must agree with the model's ordering. An open refused at `Slot::insert` is refused by the code: the driver lets the open itself succeed. Once a session's last reference has gone, nothing of it changes in the model but its handles, which have closed: the code is then compared on the session being gone (the driver's `Weak` no longer upgrades) and on the pool, and the rest is what was last read from it.
- **What is not.** The glue around the machine: `handle_request` and `handle_connection`'s IO, the resets and closes they send (and that a change given up on while it ran is answered fenced and not again, which the driver does as `handle_request` does), `Server.connections`' registry, a frame that never decodes (a cancel or a lost stream before decoding is the driver's; the code only lets the request's hold go), and how each IO event becomes a step. Trace validation, above, covers that. A session's holders match the model's `alive` here because the driver accepts every stream as it is written; the real network may lose a frame before the server accepts it, which the model's `dropCut` covers.
- **What drives it.** Every `cargo test` replays the corpus, `spec/mbt/corpus.json.gz`: the scenario runs of `session_small.qnt` and, for each witness, a run of the small instance that reaches it (not the reopen settling, which no random run of 200,000 reached; the reopen scenarios cover it), with a test that each of the server's steps and outcomes is taken at least once, and one that a run with a single outcome flipped stops at that step. `scripts/spec/mbt.sh corpus` remakes the corpus, and `check.sh` fails while it is older than the model. `scripts/spec/mbt.sh` replays random runs of the small instance, 2000 by default; a failure names the seed to run again.

Each of these breakages of the code, made by hand, stopped the corpus at the step where it parts from the model: the fence without `abandoned`; a resume that keeps `abandoned`; `begin` ignoring the epoch; the guard not uncounting `running_older`; `Handles::reserve` never finding the handle a resend answers from; a dropped session resumed whatever its holders; a connection's attachment never detaching its session; and a request keeping its hold on the session past each of its ends (stopped, cancelled, superseded as it began, superseded as it was held).

## What was learned building it

- **Apalache is not usable here, TLC is.** Apalache's bounded symbolic check of an earlier, smaller version of the model to depth 8 had not finished after 32 minutes, and the gaps' traces lay at depths of 14 to 20. TLC's explicit-state search explores `session_tiny` completely in about two and a half hours (901 million distinct states) and finds a violated invariant's trace in seconds. The 3-call instance is beyond it (over 100 million states found with the search far from done), so that instance gets the simulator and the scenario runs.
- **The simulator is a smoke test.** Random runs miss the fence mutation below in 60,000 traces and reach some witnesses once in 20,000. It stays in the full check for breadth on the larger instance, but nothing rests on it.
- **Order as ghost flags, not timestamps.** S1 and S2 are flags `begin` sets when a request begins out of order, with per-call sets of the calls that had ended; that keeps the state finite for TLC.
- **Mutations.** `scripts/spec/mutations.sh` breaks the model one way at a time and checks TLC on the tiny instance catches each: the fence without `abandoned` (S1); a change sent without waiting for `cancels == 0` (S1); a give-up that never counts the cancel (S1); a resume not zeroing `abandoned` (`countsConsistent`); a resume not moving `running` into `running_older` (S1); `begin` not refusing a stale epoch (S2); opens taken out of the ordering (S3: a resend that begins while its original still runs loses the race to insert and answers with an errno, while the original's handle stays); a resent open opening again instead of answering from the handle its original kept (S3: it fails where the original succeeded, and the original's descriptor stays); a dropped session no longer resumed while something of it lives (`S1strong`: its change still running beside the new session's); owed releases never sent (`owedNeverStuck`; S3 alone cannot see it, since quiescence then never comes); an owed release unordered, and one sent without waiting for the connection's pending cancels, which is how an open landed after its id's release (S3, G4: the released-id window only hid it while it remembered the id); an owed release sent without that wait; a reopen given up on without counting its cancel, so the release of its handle can overtake it (S3). Making the kernel's releases ordered trips nothing: one held behind the fence and then given up on is owed and sent again, so what it costs is L2, which is out of scope.
- **What building model-based testing found in the code.** The server resumed a dropped session for as long as anything held its `Arc`, which the model's `alive` (a request not ended, a connection up) does not cover: a request's task writing its reply and reading its stream's end for up to 2 s more, the blocking-pool closure of a request given up on while it waited for a thread (unbounded, should a stuck filesystem fill the pool), and the periodic report's listing of the sessions. In those windows the code resumed a session the model replaces. Nothing that ran was misordered by it, since nothing of the session was under way, but the code and the model disagreed on which session the client got. The server now counts what of a session is under way (`Holder`) and resumes a dropped one only while that is above zero; changing the model instead would have needed a step of its own for the last reference going, growing a state space TLC already needs hours for.
- **What trace validation found in the model.** Two things the code does that the model did not allow, and one the model allowed that the code cannot do. A request's task outlives its connection's, so a request read whole before the server lost the connection is still decoded, and a held one may drain and begin before its task notices; the model dropped both at the loss. And the model kept a request written after the server had lost its connection in transit forever: it kept the session counting as alive, so a session the server had dropped and closed could be resumed, and it kept quiescence, and with it S3, out of reach on those paths. Such a request is dropped as it is written now (`newReq`), requests on a lost connection go on until `dropCut`, and the full exploration and the mutations were run again.
- **Gaps the model clarified, before they were fixed.** G5, a release owed on a live connection waiting for a resume, needed a release's frame never to reach the server: a give-up before it was written (the only reset `client::exchange` makes for a release, which finishes its send side right after writing). G4 needed an id released and then forgotten before its open landed, and it had two paths beside the orphan release where the window was all that stood between a release and the open it overtook: an owed release sent without waiting for the connection's pending cancels, and a reopen given up on without being counted, whose connection is published while it runs. Both are mutations now.
